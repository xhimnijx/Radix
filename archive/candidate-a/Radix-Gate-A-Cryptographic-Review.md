# Radix Gate A — cryptographic formalization and review

**Document status:** Gate A design-review draft; not an independent cryptographic review, formal proof, implementation specification, audit, or launch approval. Prepared as a critical design review of the workspace research brief and protocol draft. It deliberately separates protocol-level relations that can be stated now from primitive instantiations that remain unselected. **Gate A is not passed. No mainnet parameters are selected here.**

**Scope:** The two proposed private-spend candidates only: (A) hidden membership in a global append-only hash tree proved by a transparent STARK, and (B) a lattice one-out-of-many / linkable-ring confidential-transaction path. This document does not resolve consensus, network privacy, data availability, monetary policy, or wallet UX.

## 1. Review disposition

The draft has the right high-level separation—note creation, private spend proof, nullifier state, and ledger data availability—but it currently treats candidate B as a family of papers rather than a specified protocol. The following are required before Gate A can be marked complete:

1. Select and pin one exact STARK construction/implementation, field, hash/permutation, Fiat–Shamir transcript, ZK masking, FRI configuration, and soundness analysis; define the circuit/AIR and reproduce a security calculation in the quantum random-oracle model (QROM).
2. Select one exact lattice OOM/LRS construction and its complete parameter set and version. SMILE reports a paper-level approximately 128-bit profile and 30 KB example, but those figures are not a Radix instantiation. The exact algorithms, lattice dimensions/moduli/noise bounds, rejection-sampling parameters, proof composition, and security reductions must be transcribed from a pinned paper/version and independently checked—not inferred from the reported headline.
3. Define a global, cross-ring double-spend tag for candidate B. A linkability property limited to identical rings is insufficient when a spender may choose a different ring on each attempt. The tag must be deterministically and uniquely bound to the same hidden note/secret across all valid ring contexts, while not identifying the ring member. Do not assume a generic LRS automatically has this property.
4. Specify a concrete candidate-B note-commitment, amount-commitment, range-proof, integer-balance proof, and recipient-discovery scheme. SMILE/BLOOM OOM proofs do not alone supply those components or a complete Radix transaction.
5. Fix exact wire encodings, malformed-input behavior, public statement ordering, circuit-to-consensus equivalence, and vector tests.

The parameter profile in §3 is suitable only as an explicit experimental target. It is not an assertion that either end-to-end candidate has 128-bit post-quantum security.

## 2. Threat model and claims

### 2.1 Assets and adversary capabilities

Assets are (i) spend authorization, (ii) note value and supply integrity, (iii) recipient/amount/spend anonymity against chain observers, (iv) wallet recovery and scan-key confidentiality, and (v) availability of transaction data needed to recover notes. The adversary may:

- read, reorder, delay, correlate, and retain all public blocks and transaction bytes indefinitely; choose decoy rings (candidate B); and perform classical or quantum offline computation subject to the stated primitive assumptions;
- create arbitrary transactions, keys, ciphertexts, malformed encodings, proofs, repeated outputs, and competing spends; adaptively select public inputs and attempt cross-transaction, cross-ring, and multi-target attacks;
- control a subset of miners, full nodes, peers, archive services, and remote wallet servers, censor transactions, cause reorgs within the consensus model, withhold data, and correlate network timing/IP metadata;
- know candidate recipients' public addresses and may own one or more recipient keys; compromise a wallet/key, exploit poor entropy, or exploit parser/circuit/implementation bugs.

The base chain's safety assumes the chosen consensus/fork-choice model and no sustained adversarial majority sufficient to rewrite accepted history. Privacy against a global network observer is not claimed. Endpoint compromise, coercion, malicious wallet software, traffic analysis, long-term data withholding, and denial of service are not solved by either proof system.

### 2.2 Desired properties (separate games, not yet proven)

- **Spend unforgeability / value conservation:** absent a valid prior note-opening and spend secret, no efficient adversary creates an accepted transaction that spends value or creates net value beyond authorized subsidy/fees. Includes range bounds, integer (not field-modular) conservation, canonical proof binding, and consensus state checks.
- **Double-spend resistance:** each note has a stable public nullifier/tag; at most one accepted spend can consume it, including within a block and across different candidate-B rings. Consensus atomically checks and inserts tags.
- **Spend anonymity:** conditioned on the transaction, public ledger, chosen-ring / global-set history, and stated assumptions, an observer cannot distinguish which spendable note was consumed beyond leakage explicitly admitted by the anonymity set, timing, transaction shape (including the exact Candidate-A memo-length leakage in §2.2.1), value/fee policy, and network metadata.
- **Value confidentiality:** values and change are hidden, and no accepted transaction can exploit modular wraparound or out-of-range values.
- **Recipient/key privacy:** a public KEM ciphertext alone does **not** establish anonymity or key privacy. The current ML-KEM design must be analyzed against observers that possess candidate recipient keys and can try decapsulation. In general, the ciphertext may let its intended recipient recognize it; candidate-key testing can reveal a recipient to an observer holding candidate secrets. Do not claim universal recipient anonymity or unlinkability without a formal game for the chosen discovery/encryption scheme.
- **Wallet recovery:** a holder of the specified view/spend secrets can find and validate their notes from available canonical data. This depends on archive/data availability and exact deterministic key derivation, which remain outside this cryptographic relation.

### 2.2.1 Explicit public and network leakage

Define the public leakage profile `L_pub` to include chain/version and anchor/state roots, transaction input/output counts, public fees and nullifiers/tags, serialized transaction/output lengths, block inclusion/timing, and (for Candidate B) ring sizes, ordered ring members and decoy-selection metadata. A global network observer may additionally learn submission timing, peer/IP metadata, and correlations; neither proof system hides this metadata. No padding, cover traffic, or network-anonymity construction is specified.

Candidate A's AES-GCM encoding leaks the **exact memo byte length**: its plaintext length is `8+64+64+4+|memo|=140+|memo|` bytes, and the 16-byte GCM tag is included in `C`, so `|C|=156+|memo|`. There is no padding in this profile; the permitted `|C|=156…668` range therefore reveals `|memo|=|C|-156` exactly. Any recipient- or spend-anonymity comparison must fix or explicitly condition on this leakage (and on the other relevant components of `L_pub`); do not describe memo contents or length as hidden merely because they are encrypted. No inference is made that Candidate B has better length privacy; its exact encoding is unselected.

### 2.3 Assumptions and quantum scope

Assumptions are component-specific: (i) SHAKE256 behaves as a suitable XOF/hash under the stated domain-separated use, with concrete quantum multi-target bounds; (ii) the selected STARK's commitment, low-degree testing, zero knowledge, knowledge soundness/extraction, and Fiat–Shamir transform remain secure in the claimed QROM model; (iii) ML-KEM-768 is implemented per FIPS 203 and its current errata, with Module-LWE security as an assumption, not a theorem for this composition; (iv) AES-256-GCM is used with per-key nonce discipline and appropriate multi-user bounds; and (v) candidate B's exact ideal/module-lattice assumptions, parameter reduction, ROM/QROM model, and rejection-sampling analyses are those of the pinned construction and must be reviewed independently. None of these assumptions implies the others. A STARK does not inherit KEM security; an LRS does not by itself provide a range proof.

A 512-bit hash output is a conservative *output length choice*, not a claim of 256-bit end-to-end security. Generic quantum collision algorithms, multi-target effects, algebraic/circuit-specific attacks, Fiat–Shamir grinding, and soundness composition must all be included. No blanket “quantum-proof” claim is authorized.

### 2.3.1 Branch-relative anchor predicate (consensus rule)

For candidate spend block `B_h` of height `h` and parent `P`, with transaction anchor height `a` and required root value `R`, define `AnchorOK(B_h,a,R)` by this ordered validation algorithm:

1. If `a>h`, reject before subtraction.
2. Resolve `A=ancestor(P,a)` on this exact parent chain. Reject if no such ancestor exists. `State_post(A)` means state after all accepted transactions in block `A` have been applied; require `R` to equal the relevant root(s) in `State_post(A)`.
3. Compute `d=checked_sub(h,a)` and require `d≥60` in this experimental policy.

Candidate A calls `AnchorOK(B_h,anchor_height,root_out)`; Candidate B calls it with `(note_root,tag_map_root)`. A root accepted only on another/sibling/orphan branch never satisfies the predicate. Reorganizations therefore require revalidation against the new candidate-parent ancestry. A global root table indexed only by height is insufficient to implement this rule.

### 2.4 Target security games (definitions, not proved claims)

Let `λ` be the security parameter, let adversaries be quantum polynomial-time (QPT) where the post-quantum claim is intended, and let all experiment outputs be canonically encoded. Define `Adv^G_A(λ)=|Pr[G_A(λ)=1]-1/2|` for distinguishing games, and `Succ^G_A(λ)=Pr[G_A(λ)=1]` for forgery/collision games. Concrete resource bounds (queries, number of users/notes, proof count, total chain horizon) must be fixed before assigning a numeric security level.

1. **Relation knowledge soundness (each proof system separately):** adversary outputs `(x,π)` with verifier acceptance, while no extractor given the adversary's oracle access/output can produce `w` such that `R(x;w)=1`. The required bound is `Succ ≤ ε_KS(λ)` in the exact classical/QROM model of the selected proof system. Do not replace this with ordinary polynomial IOP soundness: extraction and Fiat–Shamir security are additional obligations.
2. **Zero knowledge / witness indistinguishability:** for any two valid witnesses `w0,w1` for the same public `x`, the verifier's real proof views for `(x,w0)` and `(x,w1)` are computationally indistinguishable from each other and from the specified simulator's output. Bound the distinguishing advantage including transcript grinding, auxiliary chain data, and composition. For a STARK, specify the simulator and masking mechanism of the pinned construction.
3. **Commitment binding:** adversary wins by producing `(p,v,ρ,r) ≠ (p',v',ρ',r')` with `H_note-commit(p,U64(v),ρ,r)=H_note-commit(p',U64(v'),ρ',r')`. Target success is bounded by the concrete collision/second-preimage advantage for the hash and the system-wide number of commitments. This is a computational binding game, not a homomorphic commitment property.
4. **Commitment hiding:** challenger samples `b←{0,1}`, chooses equal-length messages/opening components `m0,m1` (including amount and owner component) supplied by the adversary, samples fresh independent uniform 512-bit `ρ,r`, and returns `H_note-commit(m_b,ρ,r)`. Adversary guesses `b`. The target is negligible advantage in a precisely stated random-oracle/XOF model. This game must be expanded to cover all public transcript fields; the plain-hash construction is not asserted hiding under arbitrary nonuniform or reused salts.
5. **Nullifier pseudorandomness / unlinkability:** challenge gives the adversary the full public ledger and one `nf=H_nullifier(s,K,ρ)` for a fresh note opening whose 512-bit secrets are not disclosed. In the real/ideal variant, replace `nf` by an independent uniform 512-bit string. Target distinguishing advantage is negligible after accounting for known output data, chosen notes, multi-targets, and quantum queries. This is a required hash assumption, not automatically implied by collision resistance.
6. **Spend anonymity A:** adversary adaptively receives the full ledger and may choose transactions/outputs, corrupt arbitrary non-challenge users, and disclose their view/spend keys. It then selects two distinct, mature, unspent notes at the same accepted root, with equal hidden value, public transaction shape, fee and maturity, and identical relevant `L_pub` (including any output-length/memo-length leakage); neither challenge user's spend or viewing key nor either note opening may be corrupted/disclosed. The challenger samples `b←{0,1}`, produces a valid spend of note `b` with otherwise fixed public outputs/context, and gives the full resulting transaction (including nullifier, proof, root history and all public bytes) to the adversary, who guesses `b`. Define the experiment over an explicit accepted-chain/reorg history and leakage function. The target advantage is bounded only if the joint proof is zero knowledge and nullifiers are pseudorandom in the presence of this auxiliary/adaptive ledger data. Exclude cases whose values, recipient scan keys, network timing or wallet metadata trivially identify a note; report those exclusions as leakage, not as cryptographic anonymity.
7. **Double-spend / inflation safety:** a QPT adversary controls arbitrary transaction generation and attempts to produce two accepted spends for the same note/tag in one canonical history, or an accepted state transition whose total spend exceeds valid inputs plus authorized issuance. The game includes ordered atomic nullifier/tag and commitment-set updates, range checks, root/maturity/anchor rules, mint relation, explicit genesis/migration relation, and permitted consensus reorg depth. Its success bound composes proof knowledge soundness, hash assumptions, state-transition correctness, and consensus security; no primitive alone proves it.
8. **Candidate B LRS games:** specify unforgeability (no signature/tag for a ring without any member secret), anonymity (challenge member hidden for an adversarially selected valid ring, message, ordering and decoys), and global cross-ring linkability (for adaptive chosen rings/messages, two valid signatures by the same note key always yield the same tag, including across reorderings/snapshots; signatures for distinct notes/keys have colliding tags only with negligible probability). Require one-time keys or a formally proven note-specific construction to prevent key reuse from linking unrelated notes. The third game is mandatory and is not implied by unforgeability or same-ring linkability.
9. **Recipient key-privacy / recipient anonymity:** challenger gives an adaptive QPT adversary two valid candidate addresses and any allowed public information; it chooses `b`, creates an output to address `b`, and returns the full public output and proof. Unless the adversary is explicitly denied candidate viewing secrets, the current construction is trivially distinguishable: with either `sk_v`, it decapsulates `ct_kem`, derives `K`, recomputes the candidate `cm` from candidate `pk_s` and `K`, and tests equality. Therefore no recipient-anonymity game is claimed as satisfied; ML-KEM IND-CCA is not key privacy. Any future recipient-anonymity target must precisely restrict corruptions and leakage and use a construction that survives candidate-key testing.
10. **Wallet recovery and availability:** not a cryptographic indistinguishability game. State operationally that recovery requires historical output bytes, correct view keys, and availability of chain/archive data; test adversarial withholding, retention and scanning separately. No data-availability or recovery guarantee is claimed here.

These games make the desired security statements reviewable; they are presently unproved and do not supply a numeric end-to-end level.

## 3. Common experimental encoding and primitive profile (not mainnet)

The rules below are the proposed canonical test-vector profile. Implementations must reject any noncanonical form; no parser may silently normalize inputs.

### 3.1 Byte encoding

- Octets are bytes. `U8`, `U16`, `U32`, and `U64` are unsigned little-endian integers of exactly 1, 2, 4, and 8 bytes. Reject values outside the stated range; no alternate integer encodings.
- `Bytes(x)` is `U32(len(x)) || x`, with a field-specific maximum length checked before allocation. `Vec_n(x_1,…,x_n)` is `U16(n) || Bytes(x_1)||…||Bytes(x_n)`; each protocol field fixes its count and element lengths. No maps, optional fields, duplicate keys, ignored suffix bytes, or unknown extension fields are permitted in v1.
- Fixed-width digests are exactly 64 bytes. SHAKE output is the first requested number of bytes of SHAKE256 over the entire framed input; no text encoding or implicit NUL terminators.
- `Frame(tag; x_1,…,x_n) := ASCII("RADIX") || U8(1) || U16(|tag|) || ASCII(tag) || U16(n) || Bytes(x_1)||…||Bytes(x_n)`. Tags are fixed printable ASCII strings assigned below. Each part has an explicit byte representation. Reject a tag or part list not prescribed for that call.
- `H_tag(x_1,…,x_n) := SHAKE256(Frame(tag;x_1,…,x_n), 64 bytes)`. Exact mappings: `H_spend-pk=H_"radix/spend-pk/v1"`; `H_note-owner=H_"radix/one-time/v1"`; `H_note-commit=H_"radix/note/v1"`; `H_note-leaf=H_"radix/leaf/v1"`; `H_tree-empty-leaf=H_"radix/tree-empty-leaf/v1"`; `H_tree-node=H_"radix/tree-node/v1"`; `H_nullifier=H_"radix/nullifier/v1"`; nullifier-map nodes use `H_"radix/nf-node/v1"`; Candidate-B signature messages use `H_"radix/lrs-message/v1"`. Candidate-B's composite snapshot state identifier uses `H_"radix/state-root/v1"` over `(note_root,tag_map_root)` when a single digest is required. The KDF uses the framed tag `radix/note-kdf/v1`; proof/transcript tags must be fixed by the selected proof suite. This definition replaces informal `tag || x` notation for v1.

**Candidate-A encodings (experimental v1):** `chain_id` is exactly 32 network-assigned bytes; `tx_version` is `U16` and equals 1 in this profile; `anchor_height` is `U64`; each root, commitment, nullifier and leaf is exactly 64 bytes; `fee` is `U64`. Encode an address as `Frame("radix/address/v1";chain_id,pk_s,pk_v)`, with field lengths 32, 64, and 1,184 bytes; reject a chain-id mismatch or a noncanonical ML-KEM-768 public-key encoding. The payer may still be given arbitrary valid-length `pk_s` bytes; address syntax does not prove control. Define exactly five output-frame arguments: `Serialize_output[k]=Frame("radix/output/v1";cm_k,ct_kem[k],nonce_k,C_k,leaf_k)` with field lengths 64, 1,088, 12, 156–668, and 64 bytes; `C_k` is the AES-GCM ciphertext including the 16-byte tag. Encode `Serialize_A(x_A)=Frame("radix/tx-statement/v1";chain_id,U16(tx_version),U64(anchor_height),root_out,U64(fee),Vec_m(nf_1,…,nf_m),Vec_q(Serialize_output[1],…,Serialize_output[q]))`. Here `Vec_m=U16(m)||Bytes(nf_1)||…||Bytes(nf_m)`, and `Vec_q=U16(q)||Bytes(Serialize_output[1])||…||Bytes(Serialize_output[q])`; each `Frame` also wraps each of its own arguments with `Bytes`, including the complete serialized vectors. Thus each output-vector element is the length-prefixed complete output frame, whose five fields are independently length-prefixed by that inner `Frame`. Reject invalid lengths, counts, versions, and trailing bytes. This fixes address and public relation-statement bytes, not the proof-suite-specific proof encoding or transaction-size cap; those remain to be selected and tested. Candidate B must use the same widths for shared fields but still needs a fully specified `Serialize_B`.

**Statement-length sanity check (no proof bytes):** Under the exact nesting above, `len(Serialize_A(x_A))` is 1,678–2,190 bytes for `m=q=1`, and 24,193–32,385 bytes for `m=q=16`, as each `len(C_k)` ranges from 156 to 668. The standalone tests assert all four count/length endpoints. These lengths include output-frame bytes and their `Bytes` vector-element prefixes, but exclude proof bytes, transaction-envelope bytes, and outer network framing; they are not full transaction-size limits.

**Serialization-only reference vectors:** The following deterministic fixtures check the address, output, and transaction-statement byte encodings. They are shape-valid byte strings only: the ML-KEM public key and AEAD ciphertext are dummy bytes, so they are not valid cryptographic outputs and must not be submitted as transactions. SHA-256 is used only as a test fingerprint over the encoded bytes; it is not a protocol hash. A standalone, dependency-free runnable suite is [Radix serialization test vectors](Radix-Serialization-Test-Vectors.py).

```python
import hashlib

def U16(n): return n.to_bytes(2, "little")
def U32(n): return n.to_bytes(4, "little")
def U64(n): return n.to_bytes(8, "little")
def Bytes(x): return U32(len(x)) + x
def Vec(xs): return U16(len(xs)) + bytes().join(Bytes(x) for x in xs)
def Frame(tag, xs):
    t = tag.encode("ascii")
    return b"RADIX" + b"\x01" + U16(len(t)) + t + U16(len(xs)) + b"".join(Bytes(x) for x in xs)
def seq(n): return bytes(i % 256 for i in range(n))

chain, pk_s, pk_v = seq(32), seq(64), seq(1184)
address = Frame("radix/address/v1", [chain, pk_s, pk_v])
cm, ct_kem, nonce, C, leaf = seq(64), seq(1088), seq(12), seq(156), seq(64)
output = Frame("radix/output/v1", [cm, ct_kem, nonce, C, leaf])
statement = Frame("radix/tx-statement/v1", [
    chain, U16(1), U64(60), bytes([0xA5]) * 64, U64(0),
    Vec([bytes([0x5A]) * 64]), Vec([output])
])
fixtures = {
    "address": (address, 1318, "9cb50d69354c882cf746ef92e91666eb60bea30709917dafaeb4786e6f3fbac9"),
    "output": (output, 1429, "970b4e469795fef013696122d0391dfff566caa7d627f2169876032023a49aef"),
    "statement": (statement, 1678, "845fc315a6ca599ea1046082521b9dd2ebf300d3a25148e8124dbf63d25c359f"),
}
for name, (encoded, expected_len, expected_sha256) in fixtures.items():
    assert len(encoded) == expected_len
    assert hashlib.sha256(encoded).hexdigest() == expected_sha256
```

### 3.2 Experimental common parameters

| Purpose | Experimental choice | Status / caveat |
|---|---|---|
| Domain-separated hash/XOF | SHAKE256, 512-bit output for consensus commitments, tree nodes, and nullifiers | Concrete output length. In an ideal random-oracle heuristic, generic quantum collision query complexity is about `2^(512/3) ≈ 2^170.7` and preimage search about `2^256`; these are not instantiated security bounds and do not cover multi-target/composition attacks. |
| Recipient encapsulation | ML-KEM-768 per FIPS 203; public key 1,184 bytes, ciphertext 1,088 bytes, shared secret 32 bytes | Standard parameter set, not recipient-anonymous encryption. Verify canonical key encoding and current FIPS errata. |
| Note AEAD | AES-256-GCM, 96-bit nonce, 128-bit tag; wire ciphertext includes tag; one encryption under a key derived per KEM encapsulation | Require fresh nonce; one note encryption per KEM shared secret/key. Enforce nonce/key limits and fail closed on invalid tag. |
| KDF | SHAKE256, framed `radix/note-kdf/v1`, output 32 bytes from `(K, ct_kem, cm)` | Binds each AEAD key to its note context; domain-separated prototype KDF, needs composition review. |
| Note amount | `U64`, base-unit integer; no signed or floating values | Each transaction has at most 16 inputs and 16 outputs in experimental profile. |
| Merkle set | Append-only binary tree with 64-bit leaf indices, fixed depth 64, fixed empty-subtree hashes and domain-separated left/right internal nodes | Capacity and tree initialization/root-history rules must be specified in implementation vectors. Input index/path remains witness-only. |

### 3.3 Experimental STARK knobs (not a selected proof system)

For apples-to-apples prototyping, evaluate a STARK over the Goldilocks prime field `p = 2^64 − 2^32 + 1`, trace domain a power of two, maximum trace length `2^24`, LDE blowup factor 8, FRI query count 128, and 32-bit transcript grinding. Use 512-bit SHAKE256 outputs for external transcript/Merkle commitments in this profile. These are **benchmark targets only**: they do not define a complete STARK or imply 128-bit security. In particular, 128 FRI queries do not automatically yield 128-bit soundness: the bound depends on the exact FRI/DEEP variant, degree and rate, extension field, adaptive query model, grinding, and Fiat–Shamir/QROM analysis. The field extension, exact FRI variant, degree bounds, query sampling, ZK masking rows, grinding transcript, commitment hash mapping, circuit/AIR, and soundness calculation must be fixed by the selected reviewed implementation. If the selected implementation cannot meet a documented target after QROM and composition analysis, reject or revise this profile; do not tune silently.

**Source-pinned implementation screen (benchmark only; not selected for the private spend proof).** I checked Winterfell `v0.13.1`, pinned to commit `2f78ee9bf667a561bdfcdfa68668d0f9b18b8315`, as an example of a concrete STARK configuration—not as a Radix backend. With no CLI overrides, its Merkle example uses base field `f128`, default proof hasher BLAKE3-256, 28 queries, blowup 8, grinding 16, no composition-field extension (degree 1), FRI folding factor 8, remainder maximum degree 31, linear batching for both constraint and DEEP composition, and default partition settings `(1 partition, hash_rate=1)`. The pinned source documents the query-plus-grinding term as bounded by `q·log2(blowup)+grinding`, which here is `28·3+16=100` bits; this is only one conjectured term/ceiling, not a total soundness estimate or QROM bound, and cannot substantiate the review's nominal 128-bit benchmark target. The example's application Merkle tree uses Rescue128; that is separate from its STARK commitment hasher. These are code-defined example settings, not independently benchmarked here and not asserted to meet any Radix security target. The project's own pinned README warns that it is unaudited/not production-ready and says its current implementation does **not** provide perfect zero knowledge, warning that proofs may leak information about secret inputs. That is insufficient evidence for Radix's required privacy relation absent a separate formal analysis and assurance, so I do not select this backend. It is recorded only as a code-defined toy-relation benchmark/reference point; no soundness or privacy claim follows. ## 4. Candidate A — global output tree plus transparent ZK-STARK

### 4.1 Note and leaf definitions

A recipient's public address supplies `(pk_s,pk_v)`; the payer knows these public values but does not know the recipient's spend secret `s`. A spendable note opening is `N=(s,K,rho,r,v,memo)`, where `s`, `rho`, and `r` are 64-byte strings, `K` is the 32-byte KEM shared secret, `v` is `U64`, and `memo` is at most 512 bytes. Define:

- `pk_s = H_spend-pk(s)` (64 bytes).
- `p = H_note-owner(pk_s,K)` (64 bytes).
- `cm = H_note-commit(p,U64(v),rho,r)` (64 bytes).
- `ct_kem` is exactly the 1,088-byte ML-KEM-768 encapsulation ciphertext to the recipient's `pk_v`.
- `Kenc = SHAKE256(Frame("radix/note-kdf/v1"; K,ct_kem,cm),32)`. Include `cm` to provide per-note key separation even if an encapsulation is accidentally reused. Require commitment `cm` to be globally unique in consensus state (also reject duplicates within a transaction), so one KDF context is used for at most one output encryption.
- `C = AES-256-GCM.Enc(Kenc, nonce, plaintext, AAD)`, with a 12-byte nonce sampled from a CSPRNG, plaintext `U64(v)||rho||r||Bytes(memo)` (at most 652 bytes), AAD `U8(1)||cm||ct_kem`; `C` includes the 16-byte tag. One AEAD encryption is permitted per derived key; reject authentication failures.
- `leaf = H_note-leaf(cm,ct_kem,nonce,C)` (all parts length-fixed except `C`, which is length-prefixed).

The tree has depth 64 and `2^64` indexed leaves. Define `E_0 = H_tree-empty-leaf()` and `E_{d+1}=H_tree-node(U8(d),E_d,E_d)` for `d=0,…,63`. At each level, `H_tree-node(U8(d),left,right)` is applied in left/right order; the index's bit `d` determines orientation. The empty initial root is `E_64`. A populated leaf is the `leaf` digest above; unused leaves remain `E_0`. A path consists of exactly 64 sibling digests; its direction bits are exactly the little-endian bits of its claimed `U64(index)`, not separately encoded. Root history is resolved relative to the candidate block's parent ancestry, not through a height-only global table; competing branches may have different roots at the same height. Consensus accepts only roots produced by its append-only state transition and recorded in authenticated state.

The sender samples fresh KEM coins and note randomness. The note spends only if its leaf is in the accepted tree, its commitment and encrypted recovery payload are well formed, and the spending witness proves the corresponding `s,K,rho`.

### 4.2 Public statement and relation

For fixed `m,q ∈ [1,16]`, let public statement

`x_A=(chain_id,tx_version,anchor_height,root_out,fee,[(nf_j)]_{j=1..m},[Serialize_output[k]]_{k=1..q})`, where each output frame is exactly `Frame("radix/output/v1";cm_k,ct_kem[k],nonce_k,C_k,leaf_k)`.

Wire format fixes vector order; repeated nullifiers are invalid. The nullifier set is a sparse Merkle map keyed by the full 512-bit `nf`: an unused key has value 0 and a spent key value 1, with a fixed 512-level path whose directions are the nullifier bits in the specified least-significant-bit-first order. Its node hashes use a separate `radix/nf-node/v1` domain. Full-node validators check each nullifier against the current staged map and each output `cm` against the current staged commitment-uniqueness set, including earlier transactions in the same block. Transfers are processed in serialized block order and output-vector order; mint is logically last, as specified in §4.3. A stateless transition proof is not part of the first reference prototype and, if later required, must prove old-to-new updates for every authenticated consensus-state component; the transaction relation alone does not.

Witness `w_A` contains for each input: `(s_j,K_j,rho_j,r_j,v_j,cm_j,ct_kem,j,nonce_j,C_j,index_j,path_j)`; for each output: `(pk_s,k,pk_v,k,K_k,m_k,rho'_k,r'_k,v'_k,memo_k,aead_nonce_k)`, where `pk_s,k` is an arbitrary hidden 64-byte address component supplied by the payer and `m_k` is the exact 32-byte ML-KEM encapsulation randomness input specified by FIPS 203. The relation does not prove that `pk_s,k` was derived from a spend secret or that anyone controls it; malformed/unspendable-address handling is a separate policy. The payer does not know or prove knowledge of the recipient's spend secret for an output. Also include any public-tree boundary witnesses required by the fixed tree format. The exact relation `R_A(x_A;w_A)=1` iff all of the following hold:

1. All fixed-width encodings and witness ranges are canonical; `m,q` are within bounds. `fee` and every value are `U64`.
2. For each input `j`, recompute `pk_s,j`, `p_j`, and `cm_j` from its secret/opening. Recompute the historical note `leaf_j` from `cm_j`, its original `ct_kem,j`, `nonce_j`, and `C_j`. Its 64-level path/index computes exactly to public `root_out` with canonical direction bits. For candidate spend block `B_h` at height `h` with parent `P`, require `AnchorOK(B_h,anchor_height,root_out)=1` under §2.3.1. This binds the path to the output root in the post-state at the exact ancestor, not merely to a root that once appeared at that height. This conservative snapshot delay makes every note already present in the anchor root at least 60 blocks old, covering both ordinary-note and coinbase maturity without adding unproved creation-height metadata to leaf records.
3. Recompute `nf_j = H_nullifier(s_j,K_j,rho_j)` and require exact equality with the corresponding public nullifier. Reject duplicate public nullifiers in one transaction. The consensus state check remains mandatory.
4. For each output `k`, verify `pk_v,k` is a canonical, well-formed ML-KEM-768 public key under the pinned FIPS encoding; recompute `(ct_kem,k,K_k)=ML-KEM.Encaps(pk_v,k;m_k)` exactly. Treat the witness `pk_s,k` as an arbitrary 64-byte address component (no spend-secret preimage is available to the payer); compute `p_k=H_note-owner(pk_s,k,K_k)` and `cm_k`. Require distinct `cm_k` values within this transaction; derive the KDF key including `cm_k`; encrypt the exact canonical plaintext with the prescribed AEAD inputs; recompute `C_k` and `leaf_k`; require exact equality with every public output field. Consensus rejects any `cm_k` already used by a prior output. Randomness ranges and rejection behavior are those of the fixed standard implementation.
5. Every input/output value is in `[1,2^64−1]` in this profile. `fee` is in `[0,2^64−1]`. (If zero-valued outputs are later allowed, that is a versioned relation change.)
6. Perform conservation as a bounded integer equality, not equality only modulo the proof field: `Σ_{j=1}^m v_j = Σ_{k=1}^q v'_k + fee`. With the stated caps, the input sum is `<2^68`, while the output sum plus a separately `U64` fee is `<2^69`. The circuit must constrain carries/limbs for the full 69-bit right-hand bound and prove equality as integers; a field equation alone is insufficient.
7. The proof transcript binds the exact canonical `Serialize_A(x_A)`, including chain id, transaction version, anchor height, anchor output root, fee, ordered nullifiers, and ordered outputs. **No candidate-block or fork identifier is a proof input.** Candidate-branch applicability is consensus-side: `AnchorOK` resolves the supplied root on the exact candidate parent's ancestry, while current nullifier/commitment maps are checked atomically during block execution. A proof/transaction may therefore be replayed on another branch only if its chain/version/anchor/root statement matches there; branch-specific state checks decide acceptance. Domain separation prevents cross-chain/version reuse only as provided by the selected construction's actual transcript and security analysis. The proof must provide stated zero knowledge and knowledge soundness/extraction; “STARK” alone is not a security definition.

**Important correction:** Output proof consistency shows that the ciphertext was formed under a hidden well-formed `pk_v`; it does not prove that a recipient controls the decapsulation key, that the address was honestly generated, or that observers cannot test candidate keys. Such properties require separate address-creation/recipient-discovery definitions.

### 4.3 Candidate-A issuance relation and accepted-tree invariant

The ordinary transfer relation above has `m≥1` and cannot authorize issuance. Define a separate mint statement `x_mint=(chain_id,tx_version,height,S_h,F_h,[(cm_k,ct_kem,k,nonce_k,C_k,leaf_k)]_{k=1..q})`, where `S_h` is the scheduled integer subsidy and `F_h` is recomputed by block validation as the sum of public fees in valid included transfers. `R_mintA(x_mint;w)=1` iff `1≤q≤16`, every output satisfies the exact Candidate-A output-construction checks in §4.2 item 4, all output values are in `[1,2^64−1]`, output commitments are distinct and globally unused, and `Σ_k v'_k = S_h + F_h` as an integer with sufficient wide limbs (no field or machine-integer wraparound). This profile permits no implicit burn; adding burns requires a separate public burn amount and relation. No input membership/nullifier is present. The block executor verifies this mint proof once, enforces at most one mint transaction per block, checks `height` and `S_h` against the consensus schedule, computes `F_h` from the accepted public-fee list, and atomically appends its output leaves with the other block updates. The per-block fee accumulator uses checked wide arithmetic. A consensus maximum transfer count and fee bound per block are still needed to select a finite canonical width for `F_h` and `Serialize_mintA`; neither is guessed in this draft.

**Proposed deterministic reference-block order (Gate 1 model; consensus caps remain provisional):** start from the candidate parent's post-state and create a private staging overlay. Validate ordinary transfer transactions in their serialized block order. For each transfer, verify its proof and branch-relative anchor; check every nullifier against both the parent state and earlier staged transfers; check each output commitment against the parent uniqueness set and earlier staged transfers; then append that transaction's leaves in its output-vector order, assign consecutive indices, and stage its nullifiers/commitments/fee. A duplicate or any invalid transaction rejects the entire block; no invalid transaction is skipped and no fee from it is counted. After all transfers, process exactly one mint transition as a logically last operation: verify its schedule and output sum against the checked aggregate of fees from all included transfers, check its commitments against the same staged uniqueness set, and append its outputs in vector order. Only after the whole block succeeds are the staged tree, nullifier set, commitment set and supply state committed atomically. This order prevents parallel checks against only the pre-block state from admitting same-block duplicate spends or commitments. The append counter is a 65-bit count in `[0,2^64]`; an append requires count `<2^64`, and a block that would exceed tree capacity is invalid. Exact block transaction/byte caps, canonical mint serialization, and finite aggregate-fee width must be fixed before consensus implementation.

For the first non-value reference prototype, choose **full-node state validation from genesis**: reconstruct the nullifier set and commitment-uniqueness set by replaying accepted blocks. No stateless validation, state-root proof, trusted snapshot, or compact-bootstrap claim is in scope. If stateless clients are later required, define authenticated roots for every consensus set and a complete old-to-new block transition proof as a separate protocol extension.

**Inductive tree invariant:** every leaf in every accepted root was appended by exactly one verified `R_A` transfer output or `R_mintA` issuance output, except the initial root and any migration/genesis leaves covered by a separately specified, fixed, auditable relation and explicit supply bound. The input relation does not decrypt historical AEAD ciphertexts; it relies on this invariant to establish that each included leaf's recovery payload was checked when appended. No other path may insert leaves. If issuance/migration is disabled, state this as a consensus rule; never treat an unproved genesis/coinbase output as an ordinary note.

All Candidate-A spends use `AnchorOK` from §2.3.1 with `R=root_out`; future anchors are rejected before subtraction, roots are read from the exact ancestor's post-state on the candidate branch, and the checked height difference must be at least 60. Notes in that branch-specific accepted root are thereby mature under both the provisional 10-confirmation ordinary-note and 60-confirmation coinbase rules. This is deliberately conservative; a shorter delay requires authenticated creation-height/origin metadata and a revised relation/tree format.

### 4.4 Candidate-A assumptions and principal failure modes

**Assumption ledger for Candidate A:** (i) SHAKE256 is treated as a domain-separated XOF and, where the proof argument requires it, an ideal random oracle in the classical/QROM analysis; this is a heuristic model, not a standard-level reduction. Collision/second-preimage resistance supports commitments and tree integrity, while nullifier pseudorandomness needs a separate argument for `H_nullifier(s,K,rho)` with high-entropy secret inputs and adaptive/multi-target leakage. (ii) Note-commitment binding relies on hash collision resistance; its hiding relies on high-entropy secret openings and is not an unconditional hiding theorem for a plain hash. (iii) ML-KEM-768 must meet its FIPS 203 IND-CCA security claim under the specified module-lattice assumptions, with canonical public-key checks; it does not give recipient key privacy or prove address ownership. (iv) The framed SHAKE KDF must supply per-context key separation, and AES-256-GCM must provide AEAD confidentiality/integrity under the one-encryption-per-derived-key and 96-bit nonce profile. (v) The selected exact AIR/STARK must establish zero knowledge and knowledge soundness/extractability with the analyzed FRI/commitment parameters; Fiat–Shamir must remain sound in the QROM. (vi) Consensus root/nullifier correctness and circuit/implementation equivalence are additional assumptions, not cryptographic consequences. No complete reduction or quantified end-to-end security bound is established by this draft.

Failure modes include wrong/ambiguous framing, field-modular balance, missing input path binding, witness leakage, transcript malleability, an unsound or under-masked STARK, invalid KEM public-key acceptance, recipient-key testing, nonce/key misuse, stale or unaccepted anchor roots, incorrect empty-tree logic, nullifier races, circuit/consensus divergence, and data unavailability. The current SHAKE-in-circuit cost, KEM/AES-in-circuit cost, and proof size are unmeasured. No compactness, efficiency, or anonymity-set guarantee follows from global-tree membership alone.

## 5. Candidate B — lattice OOM/LRS ring confidential transaction

### 5.1 Scope and cryptographic interface

Candidate B is **not** “SMILE or BLOOM plus a transaction.” It requires a single consistent, fully parameterized construction for all listed operations. Define an implementation package `LRS*` with algorithms `Setup(1^λ)`, `KeyGen`, `KeyFromSecret`, `Commit`, `ProveOOM`, `VerifyOOM`, `TagLinkable`, `SignLinkable`, and `VerifyLinkable`, plus lattice commitment opening/range/integer-relation proof algorithms. `TagLinkable(sk)` must be deterministic and context-independent; `SignLinkable` signs the canonical message under the ring and explicitly binds the supplied stable tag. The interface is only a composition boundary; its security cannot be assumed by notation. A concrete instantiation must map every call and output below to equations and algorithms in a pinned paper/library.

The intended public note record must include (or be committed to) a lattice spend verification key `Y_i`, a binding value commitment `V_i`, a note commitment `cm_i`, and recipient-discovery ciphertext/data. The private note opening includes the corresponding lattice signing secret, amount opening, scan/recovery material, and commitment randomness. Public ring `R_j` contains a consensus-valid ordered list of distinct candidates `(index_i, record_i, membership_path_i)` at an explicitly committed historical `state_root`; each public path authenticates `record_i` under that root. The OOM proof's set elements are the canonical encodings of the entire record (or a domain-separated digest binding all its fields), not `Y_i` alone. Merely proving membership of `Y_i` is insufficient: the proof must bind the same hidden ring member to its `V_i`, note commitment, authenticated state membership, and value opening.

### 5.2 Public statement and relation

For fixed `m,q∈[1,16]`, each input `j` has public ordered ring `R_j=(R_{j,1},…,R_{j,n_j})`, with unique canonical members and `2 ≤ n_j ≤ N_max` (`N_max` must be set from measured DoS limits). Each member includes its output index, canonical note record and authenticated path. The recorded snapshot contains `(note_root,tag_map_root)`; note paths are checked under `note_root`, and spend-tag paths under `tag_map_root`. Every ring is anchored at the same canonical composite snapshot recorded at `anchor_height`. For candidate spend block `B_h` at height `h` with parent `P`, require `AnchorOK(B_h,anchor_height,(note_root,tag_map_root))=1` under §2.3.1. This binds both roots to the post-state at the exact ancestor on the candidate's parent branch; a height-only or sibling-branch match is invalid. Let `core_B=(chain_id,tx_version,anchor_height,note_root,tag_map_root,fee,[(R_j)]_{j=1..m},[(tag_j)]_{j=1..m},[(out_k)]_{k=1..q})` and define `message_j=H_"radix/lrs-message/v1"(U16(j),Bytes(Serialize_B(core_B)))`, where `Serialize_B` is the versioned canonical serialization required before implementation. The public relation statement is

`x_B = (core_B, [(sig_j)]_{j=1..m})`.

Each `out_k` contains public output commitment(s), encrypted discovery/recovery bytes and the note-set append data. The transaction carries one canonical joint zero-knowledge proof `π_B` for the entire relation; its exact wire bytes and verifier are unselected. The joint proof must establish the *same hidden index, record, secret, and opening* across state membership, tag-map nonmembership, spend authorization, value commitment/range, and balance—not merely verify independent subproofs with unrelated witnesses. Witness `w_B` contains a hidden selected index `i_j`, membership/opening witnesses for the authenticated note state, a tag-map nonmembership path at the anchor, each input's signing secret and signature randomness, amount commitment opening, output recipient keys and encryption randomness/openings, range-proof witnesses, and integer-balance proof witnesses.

`R_B(x_B;w_B)=1` iff:

1. Each ring and ring member has canonical encoding, bounded length, no duplicates, and a valid membership path under the same snapshot `note_root`. The snapshot satisfies the checked anchor-height rule in §5.2, including rejection of future anchors and a nonnegative age of at least 60 blocks. The selected record is opened against the snapshot tag map with value 0 for its computed `tag_j`; this proves it was unspent at the anchor. The block executor additionally rejects any tag present in the current map and atomically inserts all new tags, catching spends after the anchor. Ring members already spent by the anchor may remain decoys; the anonymity game must account for this and for the published ring-selection/ordering policy. Public ring member/order metadata is transcript-bound.
2. For each input `j`, there exists exactly one witness-selected index `i_j` such that the selected ring member's `Y,V,cm` are the same member authenticated under `note_root`; the witness opens `cm` and `V` consistently, and the pinned suite's canonical `KeyFromSecret(sk_j)` reproduces exactly the selected `Y`. The OOM relation must prove existence of this index without disclosing it, while the outer joint proof reuses the same `i_j`, `sk_j`, record and openings in every conjunct. The LRS's own correctness and anonymity statement must cover the actual encoding and chosen-ring distribution.
3. For each `j`, recompute `tag_j=TagLinkable(sk_j)` and require equality with the public tag; this tag computation is deterministic and independent of ring membership, ring order, anchor, transaction message, and decoys. Then recompute `sig_j=SignLinkable(sk_j,R_j,message_j,tag_j;coins_j)` and require exact equality with the public signature. This ordering avoids circularity because `message_j` binds `tag_j`, while the tag itself does not depend on the message. The stable tag is tied to the same selected note and prevents re-ringing from evading consensus double-spend detection. Per-note signing-key uniqueness (or a formally proven note-specific tag derivation) must prevent unrelated notes from being linked merely because a key was reused. Repeated tags within one tx are invalid; consensus also checks/sets tags atomically. If the chosen LRS cannot provide cross-ring linkability with this property, candidate B is rejected or must add a separately proven PQ-safe global nullifier relation.
4. For every output, the chosen recipient-discovery protocol produces a canonical ciphertext and a hidden recipient/opening witness; output commitment, amount commitment and discovery ciphertext are mutually consistent. The relation binds a canonical one-time spend key `Y` to its secret, and consensus rejects a `Y` already used by another note, so the same LRS secret cannot silently back multiple notes. A proof of valid recipient public-key generation/ownership is required or the failure behavior for malformed/unspendable recipients is explicit. ML-KEM alone does not prove address ownership/key privacy.
5. Input and output amounts are each range-proven in `[1,2^64−1]`; `fee` is canonical `U64`. The lattice commitment scheme's binding/hiding property and range proof are bound to the exact notes used by the OOM proofs. The transaction has an integer-relation proof establishing `Σ_{j=1}^m v_j = Σ_{k=1}^q v'_k + fee` with explicit bounded carries and no reduction modulo a lattice modulus. For `m,q≤16`, constrain the input total below `2^68` and the output-plus-fee total below `2^69`. A proof only that a modular equation holds is insufficient.
6. Public fee/output fields and all proof substatements are bound to chain id, version, anchor/state root and the canonical transaction serialization. The composed proof/signature is zero knowledge for hidden member, amount, opening and recipient to the extent claimed by the individual constructions; its composition theorem must cover shared transcripts and adaptive adversaries.
7. Consensus rejects duplicate global tags, invalid membership roots, excess ring/proof resources, noncanonical encodings, and any nullifier-state conflict. All state changes are atomic and deterministic.

This is the full *required protocol relation* for the candidate, not a full or executable lattice relation. It is not yet an implementation-ready proof specification: `LRS*`, commitment, recipient-discovery, and joint-proof composition must be instantiated by exact cited algorithms and parameters. If no construction provides all required interfaces without circular or inconsistent assumptions, candidate B does not meet Gate A.

### 5.3 Candidate-B issuance and accepted-state invariant

The ordinary relation requires at least one input and cannot issue coins. Define a separate required mint relation `R_mintB(x_mintB;w)=1` over `(chain_id,tx_version,height,S_h,F_h,[(out_k)]_{k=1..q})`, with `1≤q≤16`. It has no ring, spend tag, or input witness; it must prove each output value in `[1,2^64−1]` under the same pinned Candidate-B commitment/range/recipient-discovery construction and prove `Σ_k v'_k=S_h+F_h` as an integer with checked wide arithmetic and no implicit burn. `S_h` is checked against the consensus schedule and `F_h` recomputed from included public fees. The block executor verifies at most one mint relation per block and atomically applies output/tag-map/uniqueness-set updates. The exact Candidate-B output construction is still unresolved, so this relation is a mandatory requirement, not a claim that a mint proof exists. All note-state leaves must originate from verified transfer or mint relations, except a fixed genesis/migration relation with explicit audited supply; no other insertion path is valid.

### 5.4 Candidate-B assumptions and principal failure modes

The proof must state the exact (ideal/module) lattice assumptions, dimensions/moduli/noise distributions, classical and quantum reductions, ROM/QROM treatment, Fiat–Shamir and rejection-sampling guarantees, commitment binding/hiding, OOM soundness/anonymity, ring-signature unforgeability/linkability, global-tag uniqueness, range/integer-relation soundness, and composition theorem. “Post-quantum lattice-based” is not a parameter set or reduction.

Principal failure modes: ring decoy selection exposes real member statistically; small/biased rings collapse anonymity; an LRS tag only links within one ring; tag can be ground or altered; same member appears under inconsistent metadata/commitments; lattice proof composes incorrectly with balance/range relation; modular wraparound inflates value; invalid keys/ciphertexts produce unspendable notes; ring/state proofs omit canonical snapshots; and huge signatures/proofs create DoS or storage failure. Candidate B's public ring-based anonymity is not equivalent to candidate A's global active-note set and requires decoy-policy and sampling analysis.
