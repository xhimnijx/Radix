**Version:** 0.1-draft

**Status:** Gate 1 started; not passed. Research-only, no-value scope. This log records formalization and reference-model progress; it is not an independent cryptographic review or proof-system selection.

## 1. Direction for the first feasibility experiment

Use **Candidate A (global append-only hash tree plus transparent ZK proof)** as the sole initial non-value feasibility baseline because its required relation is substantially more explicit than Candidate B's currently uninstantiated lattice OOM/LRS composition. This is an experiment selection, not a mainnet choice or security endorsement. Keep Candidate B as comparative research only until one exact construction supplies a cross-context double-spend tag, recipient discovery, commitments/ranges, and a reviewed joint proof.

The existing [Gate A review](<Radix-Gate-A-Cryptographic-Review.md>) and [Candidate-A mathematical exposition](<Radix-Candidate-A-Mathematical-Exposition.md>) state much of the target relation, but neither selects a complete STARK/FRI implementation or establishes the charter's 128-bit classical-and-quantum security target. There is no proof that Candidate A is practical or secure. The earliest acceptable prototype must be non-value and carry no security claims.

## 2. Gate 1 formalization decisions made

### D1 — Proof context and fork replay

The proof statement binds the exact serialized transaction data, including chain ID, transaction version, anchor height, anchor output root, fee, ordered nullifiers, and ordered outputs. It does **not** bind a candidate block hash or a distinct fork identifier. The transaction is created before block inclusion; branch applicability is instead checked by consensus `AnchorOK` against the candidate parent's exact ancestry. Reuse on another branch is permitted only when that branch has the same chain/version/anchor/root statement; the current branch's nullifier and commitment state then independently determines validity. This corrects conflicting wording that suggested the current statement was intrinsically fork-bound.

The canonical anchor rule is: reject future anchors before subtraction; resolve the anchor ancestor only on the candidate parent's branch; require its post-state output-tree root to equal the supplied root; require checked height difference at least 60. Reorgs require revalidation. No height-only global root lookup is valid.

### D2 — Deterministic block execution for the reference model

For the first reference model, block validation is sequential and atomic:

1. Start a staging overlay from the candidate parent's post-state.
2. Validate ordinary transfers in their serialized block order. For each transaction, verify the proof and `AnchorOK`; check nullifiers against parent state and all earlier staged transfers; check output commitments against parent state and all earlier staged outputs; then append leaves in that transaction's output-vector order and stage the nullifiers, commitments, and fee.
3. Any invalid or conflicting transaction invalidates the whole block. There is no “skip invalid transaction” rule, and no fee is counted for a rejected transaction.
4. Process exactly one mint transition last, after the ordinary transfers. It must match scheduled subsidy plus the checked sum of included transfer fees, its commitments are checked against the same staged uniqueness state, and its leaves append in output-vector order.
5. Commit all staged tree/map/supply changes only after the complete block validates. Reject any block whose output count would exceed the `2^64`-leaf tree; model the next-leaf count in 65 bits so the full-tree terminal state is representable.

Exact block transaction/byte caps, mint encoding, and aggregate-fee width remain consensus parameters for a later gate. This ordering is a reference-model rule, not yet a frozen consensus specification.

### D3 — Full-node-only state validation for the first prototype

The first non-value model reconstructs the nullifier set and commitment-uniqueness set by replaying accepted blocks from genesis. It does not claim stateless validation, a committed composite state root, trusted snapshots, or compact bootstrap. A future stateless/light-client design must specify authenticated roots and a complete old-to-new transition proof for every consensus state component.

### D4 — Memo length is not acceptable leakage for the privacy target

The current Candidate-A experimental encoding reveals exact memo length because its AES-GCM ciphertext length is `156 + memo_length`. The successor privacy profile should use a fixed 652-byte plaintext and 668-byte AES-GCM ciphertext for every output: `U64(value) || rho[64] || r[64] || U32(memo_length) || memo[0..memo_length] || zero_padding[512-memo_length]`. The reference model now tests that formatter/decoder, checks `memo_length ≤ 512`, rejects nonzero padding, and confirms constant ciphertext length; this is not AES-GCM, a wire-format parser, or a cryptographic test. The existing variable-length v1 vectors remain historical test vectors and must not be represented as satisfying the privacy target. Exact version/tag migration and full vectors remain to be implemented before any protocol freeze.

### D5 — Concrete reference crypto and key representation

The Python reference now pins `cryptography==50.0.2` and provides real ML-KEM-768 and AES-256-GCM adapters. The adapter stores/restores pyca's 64-byte FIPS 203 `d || z` key-generation seed; it does not import/export the expanded 2,400-byte `DecapsulationKey` encoding. ML-KEM public-key input validation checks the 1,184-byte length, all packed 12-bit coefficients `<3329`, and backend parsing; generated/restored public/private pairs are recomputed and compared. This establishes implementation checks, not formal certification or independent FIPS validation. AES-GCM has a NIST empty-plaintext test vector and tamper/AAD rejection tests. The real-provider integration remains a non-production reference backend.

### D6 — Persistent nonce history and encrypted wallet backup

The reference adds an explicit SQLite nonce registry using WAL, `synchronous=FULL`, a unique domain-separated key/nonce fingerprint, and a transaction committed before AES-GCM encryption; records are never evicted, and cross-instance/process uniqueness is tested. It assumes trusted local storage and cannot detect deletion, cloning, or rollback to an older backup. The optional encrypted wallet file uses Scrypt (`N=2^15,r=8,p=1`) plus AES-256-GCM and refuses overwrite; key/password memory is not zeroized, OS ACLs/backups remain user-managed, and no mnemonic/seed derivation or anti-rollback exists. These functions address prototype lifecycle gaps but do not make a production wallet.

## 3. Charter requirement not currently met: recipient privacy

The current construction is not sufficient to claim recipient anonymity under the approved charter. An observer who obtains a candidate recipient's viewing secret can decapsulate each KEM ciphertext, derive the AEAD key, decrypt the payload, and test it against that recipient's known public spend component/commitment. ML-KEM IND-CCA security does not rule out this candidate-key test. The present design may still protect recipients from observers who lack relevant viewing secrets, but this narrower property is not a substitute for the approved recipient-privacy objective.

**Stop condition:** do not claim Candidate A meets the charter's recipient-privacy requirement unless (a) a precise corruption/leakage game is approved and passes independent review, or (b) a different recipient-discovery construction prevents the unacceptable key-testing/linkability attack and is integrated into the proof relation. If no feasible post-quantum design satisfies the goal within the resource envelope, redesign or stop rather than silently narrowing marketing claims.

**Implementation decision (2026-10-31): no recipient-key privacy construction selected.** The reference implementation retains one ML-KEM encapsulation to the static address viewing key solely to exercise the non-value wallet flow. This does not establish key privacy: ML-KEM IND-CCA does not imply ciphertext anonymity/key privacy, and an observer with a candidate viewing secret can test candidate outputs. The protocol draft's proposed PQ stealth-address and LRS/OOM lines remain research candidates only; none is adopted without a concrete adversary game, exact protocol/relation, and evidence for linkability, metadata, ownership, and scan-cost behavior. This is an explicit unresolved P0 blocker, not a security feature of the new backend.

Related limitation: the relation accepts arbitrary hidden `pk_s` bytes and does not prove that anyone controls the spend secret or KEM decapsulation key. The sender can create an unspendable output. Wallet warnings, address checks, failure recovery, and/or a cryptographic proof-of-possession design remain open; canonical KEM-key encoding alone does not prove control.

### Dated implementation update (2026-10-31): linked two-level path AIR

The Rust harness now contains an experimental single-AIR relation for exactly two Candidate-A tree levels. It computes the first private node from the leaf and sibling using direction bit 0, links that constrained digest as the next node's current child, then computes the parent at level 1 using direction bit 1 and binds the final digest to an externally supplied root. This is a linked depth-2 path subrelation only; it does not establish depth-64 membership or bind a source output leaf/transaction statement.

During debugging, same-config verification exposed an invalid selector construction: `is_transition()` is an unnormalized polynomial selector, not a Boolean. The node-boundary event is now formed only from Boolean trace columns (`final_step` and stage bits), and transition is multiplied outside that event when gating boundary versus persistence constraints. A fixed known-answer path passes same-config proof verification and cross-checks its level-0 node against the standalone node proof. The focused Rust path tests pass (2 passed, 60.91 seconds); they reject a changed expected root, malformed magic, truncation, trailing bytes, a tampered proof payload byte, changed sibling, and direction substitutions. CLI prove/verify round trip succeeded with a 224,534-byte envelope/proof, and CLI verification rejected a substituted expected root. Python reference tests pass (107 passed in 2.58 seconds). Final validation with proof-payload mutation included: Rust suite 21 passed, 0 failed in 114.11 seconds; MSVC stable `cargo fmt --all -- --check` passed. The component remains research-only, with no depth-64, quantified-soundness, established ZK, PQ, transaction, or consensus claim.

### Dated implementation/design update (2026-10-31): depth-64 path AIR design (unimplemented)

A single-STARK implementation appears structurally feasible: exactly 64 path levels, with two 24-round Keccak permutations per framed tree-node hash, for 3,072 active round rows. The path witness should keep only the current 64-byte node and current 64-byte sibling bit-vectors in trace columns; a single private direction bit can vary once at each level boundary, making its 64 successive Boolean values the private `u64` index in LSB-first order without an in-trace 64-bit selector. A 7-bit level counter must begin at 0, advance only after each active phase-1 hash, reach 64 after level 63, and then deactivate. At each level, mux `(current,sibling)` or `(sibling,current)` from the private direction bit, constrain the exact Candidate-A frame and two-block SHAKE absorption, feed each output digest into the next level's current node, and compare only the final digest with the verifier-supplied public root. A trace with 8,192 rows may fit 128 real permutations plus 213 valid dummy permutations and 8 partial rows, but this padding/layout has not yet been implemented or proven sound; it must be tested against the pinned KeccakAir transition constraints. With 1,088 rate-output bits, 1,024 current/sibling bits, seven level bits, and active/phase/direction flags, the rough width is `NUM_KECCAK_COLS + 2,122` columns, implying significant memory/proving cost. This design is only an engineering hypothesis: benchmark and adversarially test it, bind the expected root externally rather than trusting an envelope field, and do not confuse root membership with source-leaf validity, append-count eligibility, transaction binding, or consensus validity.
