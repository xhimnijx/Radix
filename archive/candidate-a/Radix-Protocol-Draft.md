# Radix Protocol Specification (Research Draft)

**Version:** 0.1 — 2026-10-31  
**Status:** proposed architecture / research specification, **not production-ready**. No new cryptographic construction in this document has a security proof or audit. Do not deploy or assign monetary value based on this draft. The purpose is to make the engineering and mathematical questions concrete enough to prototype and review.

> **Name warning:** “Radix” and “XRD” are already associated with an existing crypto project. Treat Radix as a codename until trademark, domain, ticker, and ecosystem-confusion review is complete.

## 0. Design goals and non-goals

Goals:
1. Private-by-default transfers: hide recipient, amount, and which prior note is spent; prevent double-spends and inflation.
2. Conservative post-quantum assumptions: avoid elliptic-curve discrete-log dependence in transaction authorization, commitments, and privacy proofs.
3. Anyone can validate consensus, and users can recover wallets from chain data plus their keys.
4. Avoid requiring every validating node to retain every historical byte forever; make archival/data availability an explicit network service.
5. Preserve protocol upgradeability and crypto agility.

Non-goals: this draft does not promise anonymity against endpoint compromise, network-layer traffic analysis, KYC datasets, coercion, malicious wallets, or a global metadata observer. “Quantum resistant” means only that the chosen primitives are believed resistant to known quantum attacks under stated assumptions; it is not a guarantee against future cryptanalysis.

## 1. Proposed architecture at a glance

Radix is a proof-of-work, shielded note ledger. A transaction consumes hidden notes and creates hidden notes. Each output is a salted hash commitment, carries an ML-KEM-encrypted recovery payload, and is appended to a Merkle tree. A transparent zero-knowledge proof (STARK/FRI family) proves note ownership, tree membership, correct output construction, amount range and conservation. A hash-derived nullifier is public and globally unique; it reveals that a note was spent but should not reveal which note in the output tree was used.

**Candidate primitives for the first prototype (not final selection):**
- `H = SHAKE256` with 512-bit output and domain separation for commitments, Merkle hashing, key derivation and nullifiers.
- ML-KEM-768 (FIPS 203) for recipient note encryption.
- AES-256-GCM for authenticated note plaintext encryption, keyed from the KEM shared secret with a domain-separated KDF.
- A transparent zero-knowledge proof system using a hash-based polynomial commitment / FRI (STARK-family), with Fiat–Shamir instantiated using a 512-bit-output hash and explicit quantum random-oracle-model analysis.

Why these are candidates: this avoids relying directly on EC discrete log in the core spend relation. It does **not** mean that composing these primitives is already a secure coin. The ZK statement, Fiat–Shamir transform, quantum soundness margin, implementation, and circuit must be reviewed as one system. ML-KEM security rests on module-LWE assumptions; the hash and STARK security is separate.

## 2. Mathematical notation and domains

- Every `H_*` symbol below is the domain-separated SHAKE256 mapping with exact `Frame` encoding defined in [Radix-Gate-A-Cryptographic-Review.md](Radix-Gate-A-Cryptographic-Review.md) §3.1. Earlier `H(tag || x)` shorthand is superseded; reject non-canonical encodings.
- `s` is a 64-byte random spend secret. `pk_s=H_spend-pk(s)` is a 64-byte public spend commitment.
- Recipient viewing key pair is `(pk_v, sk_v)=ML-KEM.KeyGen()` (ML-KEM-768). Address bytes use `Frame("radix/address/v1";chain_id,pk_s,pk_v)` as defined in Gate A §3.1; `pk_s` and `pk_v` are shared with payers. The secret `s` and `sk_v` are held by the recipient. Separate spending and viewing secrets enable view-only access, but sharing `sk_v` exposes incoming note data.
- `K` is the 256-bit ML-KEM shared secret for an output, `rho` is 512 random bits, `r` is 512 random blinding bits, and amount `v` is an unsigned 64-bit integer in base units.

A public address is therefore large (ML-KEM-768 public key is 1,184 bytes, plus the spend commitment and encoding). This is one-time address data, not on-chain output size. Address rotation and subaddress derivation are not specified yet.

### 2.1 Note construction

For each output, payer obtains recipient address `(pk_s, pk_v)` and runs:

1. `(ct_kem, K) = ML-KEM.Encaps(pk_v)`.
2. `p=H_note-owner(pk_s,K)`. 
3. `cm=H_note-commit(p,U64(v),rho,r)`. 
4. `note_plain=U64(v)||rho||r||Bytes(memo)`, with `memo` at most 512 bytes. 
5. `K_enc=SHAKE256(Frame("radix/note-kdf/v1";K,ct_kem,cm),32 bytes)`; encrypt `note_plain` using AES-256-GCM with a fresh 12-byte nonce and associated data `U8(1)||cm||ct_kem`. `C` is ciphertext concatenated with the 16-byte GCM tag. The KDF binds the AEAD key to the note commitment; this encoding is defined in [Radix-Gate-A-Cryptographic-Review.md](Radix-Gate-A-Cryptographic-Review.md).
6. Output leaf `leaf=H_note-leaf(cm,ct_kem,nonce,C)`. 

The public chain sees a commitment, KEM ciphertext, nonce and authenticated ciphertext. It does not see `pk_s`, `pk_v`, `K`, `v`, `rho`, or `r`. Recipient tries `ML-KEM.Decaps(sk_v, ct_kem)`, derives `p`, decrypts and checks that the note commitment recomputes. This requires scanning/decrypting candidate outputs; watch-only wallets can hold `sk_v` without `s`. Experimental-v1 uses a variable-length plaintext, so `|C|=156+|memo|` bytes and the public ciphertext length reveals the memo length exactly. This is explicit metadata leakage, not memo privacy. The separate zero-padded proposal would produce a constant 668-byte ciphertext under AES-GCM, but it is unactivated and lacks a complete profile selector/wire format.

**Public data-size consequence:** ML-KEM-768 ciphertext is 1,088 bytes per output, before note ciphertext, commitment and proof. Two outputs alone incur at least 2,176 bytes of KEM ciphertext. This is a substantial and deliberate quantum-safe privacy cost. It is not yet known whether a different PQ encryption / scanning construction can reduce this without weakening recipient privacy.

### 2.2 Spend nullifier

For a note with spend secret `s`, KEM shared secret `K`, and `rho`, define:

`nf=H_nullifier(s,K,rho)`. The mapping uses the exact `Frame` encoding from Gate A §3.1.

Only `nf` is published when spending. A consensus state map must reject a nullifier already present. Under the intended hash/PRF-like assumptions, the nullifier is deterministic for that note and does not publicly reveal the leaf commitment. A quantum adversary who later learns `K` but not `s` should still be unable to compute `nf`; if `s` is compromised, the note is compromised. Detailed multi-target and quantum security analysis is required.

### 2.3 Hash-commitment assumptions

A note commitment is computationally hiding for uniformly random `rho,r`, and computationally binding if finding collisions/preimages for the selected hash is infeasible. Unlike Pedersen commitments, it is not additively homomorphic; therefore transaction balance is enforced inside the ZK circuit, not by summing public commitments. 512-bit hash output is selected to leave margin against generic quantum collision search, but this is not by itself a formal 128-bit security proof for the entire protocol. Parameter selection must account for multi-target attacks, quantum collision algorithms, and proof-system soundness composition.

## 3. Transaction proof relation

A transaction has public data:

The public transaction statement is `x_A=(chain_id,tx_version,anchor_height,root_out,fee,[(nf_j)]_{j=1..m},[(out_k)]_{k=1..q})`, in the same order as `Serialize_A` in Gate A §3.1. Each public `out_k` includes `cm`, `ct_kem`, nonce, complete AEAD ciphertext/tag `C`, and `leaf`; `leaf=H_note-leaf(cm,ct_kem,nonce,C)` and excludes the `leaf` field itself.

For a candidate spend block `B_h` at height `h` with parent `P`, first reject `anchor_height>h`; then resolve `A=ancestor(P,anchor_height)` on that exact parent chain, require `A` to exist, and require `root_out` to equal the output-tree root in the post-state after applying all accepted transactions in `A`. Any supplied root that differs from this ancestor's post-state root is invalid, even if it was accepted on an orphaned branch at the same height. Compute the height difference with checked subtraction and require `h-anchor_height≥60` under the current Candidate-A experimental policy. A reorganization changes which historical root satisfies this rule, so transactions must be revalidated against the new parent branch. The public nullifiers are checked against the current consensus nullifier map during ordered block execution; they are not required to share a stale transaction-level nullifier root. The reference API binds the output-tree root to its parent header but the header does not authenticate the nullifier or commitment sets. Therefore validators must derive these maps by ordered replay from genesis; a manually supplied or otherwise unauthenticated parent snapshot can bypass uniqueness checks and is not consensus-valid. This model does not claim stateless validation; any later stateless/block-transition proof or trusted checkpoint format must authenticate and update every consensus state component. The witness for each input note `j` is:

`w_j = (s_j, K_j, rho_j, r_j, v_j, p_j, cm_j, ct_kem,j, nonce_j, complete ciphertext/tag_j, MerkleIndex_j, MerklePath_j)`. The relation reconstructs the exact historical leaf preimage before checking membership.

For each output `k`, the witness contains `(pk_s,k, pk_v,k, K_k, m_k, rho_k, r_k, v_k, memo_k, nonce_k)`, where `m_k` is the 32-byte ML-KEM encapsulation randomness and `pk_s,k` is the payer-supplied 64-byte address component. The relation treats `pk_s,k` as arbitrary bytes: it does not prove derivation from a spend secret or recipient control (a sender can deliberately pay an unspendable address). The relation reproduces the public ciphertext and commitment using the exact KDF/AEAD framing in the Gate A review.

The zero-knowledge relation `R_A(x_A; w)=1` checks all of the following:

1. Each input leaf is a member of the output Merkle tree with root `root_out`.
2. For every input, compute `pk_s,j=H_spend-pk(s_j)` and `p_j=H_note-owner(pk_s,j,K_j)`; recompute `cm_j=H_note-commit(p_j,U64(v_j),rho_j,r_j)`. Each `H_*` uses the exact `Frame` encoding and domain mapping in Gate A §3.1.
3. Each published nullifier equals `H_nullifier(s_j,K_j,rho_j)` under the Gate A §3.1 framing and mapping.
4. For every output, ML-KEM encapsulation and AEAD encryption recompute exactly to its public fields, `p_k=H_note-owner(pk_s,k,K_k)` and `cm_k=H_note-commit(p_k,U64(v'_k),rho_k,r_k)` recompute, and `leaf_k=H_note-leaf(cm_k,ct_kem,k,nonce_k,C_k)` is correct, all under the Gate A §3.1 canonical framing. This makes the encrypted recovery payload consistent with the committed note. **This circuit includes ML-KEM and AES operations; proof cost may be prohibitive and must be benchmarked.**
5. Every input/output note amount is in `[1,2^64−1]` in the current experimental relation; `fee` is a canonical `U64`.
6. `Σ_j v_j = Σ_k v'_k + fee` using integer arithmetic with an explicitly bounded accumulator (no modular wraparound); with at most 16 inputs and 16 outputs of at most `2^64−1`, the input sum is below `2^68`, while the output sum plus a separately unsigned 64-bit fee is below `2^69`. The circuit must prove bounded integer equality with explicit carry/limb constraints, not merely equality modulo its field. Fee is a canonical unsigned 64-bit base-unit value. Proposed maximum `m,q ≤ 16` per transaction is a DoS/performance limit, subject to measurement.
7. This version forbids zero-valued input/output notes. Allowing zero values requires an explicit versioned relation change.
8. The proof transcript binds the exact canonical public statement (`chain_id`, transaction version, anchor height and output root, fee, ordered nullifiers and outputs). It does **not** include the candidate block hash/fork identifier: the proof is generated before inclusion, and branch applicability is checked by consensus `AnchorOK` against the exact candidate parent's ancestry. A transaction may be replayed on another branch only when that branch has the same chain/version/anchor/root context; current nullifier and commitment state checks are branch-relative and atomic. The selected proof suite must bind every serialized public field in its transcript and separately justify zero knowledge, knowledge soundness/extraction and non-malleability under its stated model.

A valid proof establishes that outputs were encrypted to a hidden, well-formed ML-KEM public key and that commitment/ciphertext fields are mutually consistent; validators do not learn the recipient or amount. It does not prove that anyone controls the decapsulation key or that the payer-supplied `pk_s` bytes were derived from a spend secret. The receiver independently checks successful decryption and commitment opening. Invalid or malicious addresses can still receive unspendable funds if the sender intentionally pays a bad address; wallets must validate address encodings and key generation. There is no proof that a recipient knows the private key unless the address protocol adds a proof-of-possession. This draft's ordinary generated ML-KEM address is assumed valid; this assumption needs a protocol solution.

### 3.1 Nullifier membership and state transition

The output commitment tree is append-only. Separately, the nullifier set is a sparse Merkle map keyed by `nf`; a leaf is `0` if unused and `1` if spent. The Gate 1 reference execution order is sequential: start from parent state, validate ordinary transfer transactions in serialized block order, and for each transaction verify its proof/branch-relative anchor, check nullifiers and commitments against both parent state and earlier staged transactions, then append its output leaves in output-vector order and stage its nullifiers, commitments, and fee. Any invalid/conflicting transaction rejects the entire block; none is skipped. After all transfers, exactly one mint operation is processed last, with outputs uniqueness-checked against the same staged set and appended in output-vector order; its amount must equal scheduled subsidy plus checked fees from included transfers. The block's staged state is committed atomically only after all operations succeed. A 65-bit leaf count represents `[0,2^64]`; appending when already at `2^64` leaves is invalid. Reject any populated output leaf whose digest equals `empty_leaf=H_tree-empty-leaf()`: otherwise a populated prefix could have the same root as an empty tree while having a different leaf count. The exact block caps and finite fee-accumulator width remain unfixed. The transaction proof establishes each public nullifier is derived from a hidden input; it does not prove sparse-map nonmembership. The first non-value reference model uses full validators replaying state from genesis and makes no stateless-validation or trusted-snapshot claim. A stateless design would require authenticated roots and a complete old-to-new transition proof for every consensus state component.

With the full 512-bit nullifier as the sparse-map key, a 512-level tree has 32 KiB of 512-bit siblings per raw nonmembership path. Paths need not be published by ordinary full-state transactions. The first reference prototype is full-node-only; if stateless validation is later required, compare sparse Merkle maps, batch-update proof systems and other PQ-safe authenticated dictionaries, and account for hiding/batching those paths. RSA accumulators are not a safe default because factoring is quantum-vulnerable; elliptic-curve accumulators are likewise unsuitable. Any future accumulator must be hash-based or supported by a separate post-quantum argument.

### 3.2 Privacy set and decoys

The proof lets a spender prove membership of one or more hidden notes in the complete output tree, rather than selecting a public ring. This avoids explicit decoy sampling, but anonymity is bounded by valid, unspent notes that are plausibly spendable at the chosen anchor. Timing, output size, fees, network broadcast and a small active note set can still deanonymize. A spend proof must conceal the Merkle index/path; never publish it.

## 4. Proof system and the honest state of the art

Candidate: transparent zero-knowledge STARK with FRI-style low-degree testing, hash-based commitments, and recursive aggregation as a later optimization. The proof proves the relation above; it is not merely a validity hash. Use no trusted setup in the candidate profile.

This is a **conditional construction outline**, not a security proof and not evidence that the components compose securely. There is no “mathematics that is automatically more secure” simply because it is newer or uses larger numbers. A STARK's security does not automatically transfer to SHAKE commitments or ML-KEM; each layer must be analyzed. Fiat–Shamir security needs a suitable quantum random-oracle-model justification. Candidate systems must state soundness error `ε`, ZK simulation properties, query counts, field size, blowup factor, grinding resistance, proof-of-knowledge/extraction, and post-quantum reductions. A 512-bit digest does not establish 128-bit system security. For generic quantum collision search, an n-bit hash has an approximately 2^(n/3) query collision attack in the BHT model; 384 bits is a plausible starting point for 128-bit generic collision work, not a formal hash-security certification. Quantum preimage search is roughly square-root. Multi-target and composition effects still apply. SHAKE's circuit cost is a major open benchmark; algebraic hashes may be cheaper in a circuit but have different assumptions and cryptanalysis.

A further unresolved condition is **recipient anonymity/key privacy**: the public KEM ciphertext and proof must not let observers identify or link the recipient. ML-KEM is a KEM, not automatically a key-private anonymous encryption scheme. A formal multi-user ciphertext/key privacy analysis is needed for hiding the static `pk_v`; do not claim unlinkability merely because that key is omitted from cleartext. The output proof must bind the encrypted note to the hidden recipient key and commitment while hiding the key. Wallet scanning cost is naively one KEM decapsulation per output per scan key, i.e. grows linearly with chain outputs. View tags or filters may improve cost but leak information and require a separate design.

The current Python reference wallet deliberately keeps the static per-address ML-KEM design only as an executable non-value baseline; the concrete ML-KEM/AES implementation does not improve or resolve this recipient-key privacy property, and no alternative is selected. It validates packed ML-KEM public encodings and generated keypair consistency for API safety, but this is not a proof of recipient ownership or a production key-validation certification.

A smart-contract/transaction proof cannot be selected by paper name alone. Before production, choose a reviewed implementation, publish exact parameter sets, prove the circuit corresponds to consensus, and reproduce benchmarks. No transaction-size claim is made here: expected proof bytes and proving time are unknown, especially because ML-KEM and AES are inside the output relation.

### 4.1 Published post-quantum alternatives to the STARK note-membership path

The current global output-tree + STARK proposal is not the only plausible PQ route. Published lattice-based linkable ring signatures (LRS) and one-out-of-many (OOM) proofs exist. They are research constructions, not standardized, interchangeable, or automatically production-ready; their assumptions differ (e.g. NTRU-, ideal-lattice-, and module-lattice-related assumptions), so “lattice-based” is not a uniform security guarantee. An LRS offers a *ring* anonymity set selected by the transaction, while the current STARK proposal hides membership in a global commitment tree; this changes the anonymity model, decoy requirements, metadata, and circuit/proof design. LRS does not replace amount-conservation/range proofs, recipient discovery, or network-layer privacy.

| Candidate | Published evidence | Relevance / limitation |
|---|---|---|
| **Raptor** (lattice LRS) | Authors report implementation, classical-comparable speed, and roughly 1.3 KB per ring member; security is argued in the random-oracle model. | Useful implementation/benchmark baseline for small rings. Linear proof growth makes large rings expensive; it is not a standardized, hardened coin protocol. |
| **SMILE** (ideal-lattice set membership/LRS) | Paper reports 16 KB for a 32-member set, 22 KB for `2^25`, and an optimized two-input/two-output confidential-transaction example around 30 KB with each input among `2^15` accounts, at approximately 128-bit security. | Most directly relevant published comparison for a Monero-like PQ confidential-payment path. Its assumptions, exact parameters, proofs, and implementation need independent review; paper figures are not Radix benchmarks. |
| **BLOOM** (lattice OOM) | Provides lattice OOM proofs and ring/group-signature constructions; authors report 25%–2x signature-size improvements against prior schemes and smaller public keys. | Worth evaluating as a proof building block alongside SMILE. Not a drop-in confidential transaction protocol. |
| **Calamari/Falafl** (lattice instantiation) | For an 8-member ring, paper reports about 30 KB signatures and 90 ms signing for the lattice scheme; smaller than compared prior schemes only beyond roughly 1,024 members. | Useful scaling comparison; poor fit if small rings and compact txs are primary. Do not assume the isogeny instantiation is a safe substitute. |
| **Code-based OOM** | A 2024 construction reports logarithmic-size OOM/ring/group-signature results; its 144 KB figure at `2^20` members is for the group signature, not the ring signature. | A different assumption family for exploration; the cited result does not imply compact coin transactions. |

A separate published line addresses PQ stealth-address discovery: [Post-Quantum Stealth Address Protocols](https://eprint.iacr.org/2025/112) proposes LWE, Ring-LWE and Module-LWE protocols; the authors report a Module-LWE/Kyber design with about 66.8% less ephemeral-public-key-registry scan time than their ECPDKSAP comparison. This is a preprint and its measured result is specific to that paper's registry/workload, not proof that the current per-output ML-KEM scheme is faster or more private. Evaluate it as an alternative discovery protocol and review recipient anonymity, linkability, metadata leakage, key ownership, and compatibility with the note/zk relation before adopting it.

The current output design's per-output ML-KEM encapsulation remains a simple, explicit prototype hypothesis, not the preferred final scheme. Compare it against the PQ stealth-address proposals and measure full-wallet scan throughput, output size, false positives, and leakage. Similarly, use [LaZer](https://eprint.iacr.org/2024/1846) as a possible lattice-ZK prototyping reference—not as a ready-made Radix protocol or security certification. PQ anonymous credentials are also an active research area (e.g. [Bootle et al.](https://eprint.iacr.org/2023/560), with proofs reported in the tens of KB and specialized lattice assumptions), but credentials are not required for a permissionless coin's base spend path. ML-DSA or SLH-DSA signatures alone do not provide anonymous credentials, LRS, or OOM proofs. [SPIRIT](https://eprint.iacr.org/2023/1148) studies PQ stealth signatures and fuzzy tracking; it is related to, but not the same primitive as, a coin stealth address or linkable ring signature.

**Updated research recommendation:** benchmark two end-to-end privacy architectures before selecting one: (A) global hash-tree membership with a transparent STARK (this draft's current candidate), and (B) a lattice set-membership/LRS confidential-transaction design based on SMILE/BLOOM-era techniques, paired with a separately reviewed PQ recipient-discovery protocol. Raptor is a useful low-complexity LRS benchmark. Compare complete transactions, proof generation/verification, wallet scanning, key/ciphertext sizes, anonymity degradation, DoS bounds, and security assumptions—not isolated signature size. None can yet be called the clear winner for this coin.

## 5. Network and consensus (provisional choices)

### 5.1 Base chain

- PoW longest/heaviest valid chain with a 120-second target block interval; median-time-past and a documented retarget algorithm. Timestamp and difficulty rules must be deterministic and tested against time-warp/manipulation attacks.
- Provisional PoW candidate: use upstream RandomX unchanged, pinned to an exact release/spec and test vectors; do not invent or tune a Radix variant. Do not describe RandomX as ASIC-proof or quantum-proof. It is CPU-oriented, and validators' initialization/verification costs must be benchmarked on minimum-spec nodes. Define a blockchain-derived seed schedule, exact serialization, reference outputs and reorg-boundary behavior before activation.
- Canonical header includes network/chain ID, protocol version, previous-block hash, transaction/state roots, timestamp, nonce and PoW-seed identifier, all with fixed/canonical encoding. Define `H = RandomX(header)` and accept iff the unsigned 256-bit little-endian hash is `≤ target`. Expected hashes at fixed target are approximately `2^256/(target+1)`.
- Chain selection is by cumulative work, not height: `chainwork = Σ floor(2^256/(target_i+1))`, with wide integer arithmetic, explicit target bounds and test vectors. Fork choice and reorg handling are deterministic from these rules.
- Provisional difficulty rule for testnet study: target interval `τ=120 s`, window `W=60` blocks; at a retarget boundary use the elapsed median-time-past between the two window endpoints, clamp elapsed to `[Wτ/4, 4Wτ]`, then `target_new = clamp(target_min,target_max, floor(target_old·elapsed/(Wτ)))`. Exact endpoint heights, first-window behavior, integer rounding and min/max target must be frozen in code and vectors before consensus. Simulate hash-rate exits and timestamp attacks; replace this candidate with a reviewed established algorithm if it performs poorly.
- Transactions are validated by every full node: syntax, proof validity, note/nullifier state transition, fees, weight, timestamp, PoW and subsidy. Miners cannot create valid proofs or bypass conservation.
- Experimental maturity rule for Candidate A: for candidate spend block `B_h` of height `h` with parent `P`, first reject `anchor_height>h`; then resolve the anchor ancestor `A=ancestor(P,anchor_height)` on that exact parent branch and require `root_out` to equal the output-tree root in the post-state after all accepted transactions in `A`; reject any root that differs from that ancestor's post-state root, even if the supplied root was accepted on a sibling/orphan branch at the same height. Compute the age with checked subtraction and require `h-anchor_height≥60`. This conservatively makes every note in that branch-specific snapshot old enough for both the provisional 10-confirmation ordinary-note and 60-confirmation coinbase rules; it imposes a 60-block minimum anchor delay on all notes, stricter than the ordinary-note maturity target. A shorter per-note delay requires authenticated creation-height/origin metadata in the tree leaf and a revised proof relation. PoW confirmations are probabilistic, not deterministic finality; wallets should report depth/risk, not call a fixed number final. Reorgs require revalidation against the new parent branch.
- Consensus upgrades use explicit activation heights and versioned proof domains; no silent crypto swaps.

### 5.2 Block resource limits and fees

Do not set an arbitrary fixed byte target before proof and bandwidth benchmarks. Count consensus “weight” as actual serialized bytes plus measured verification/proving resource charges. Enforce per-transaction caps, per-block caps, proof-verification budget and mempool fee floor. A block-size feedback rule must not reward miners for bloating the chain; cap growth and use recent median weight. Derive limits from commodity-node benchmarking and censorship-resistance analysis. Every cryptographic operation and output is a DoS surface.

**Node-retention gate:** before freezing a proof/transaction format, publish a 15-year local-storage budget for a lightweight individual pruned node. Its acceptance target is strictly less than 1 TB decimal of total retained data, including its bounded recent window, headers/checkpoints, authenticated current state, proof data, indexes, measured database overhead, and operational headroom. The full archive has no size target and may be arbitrarily larger; archive capacity is outside this gate, though independent archive/data-availability service remains necessary. This is a design target to validate, not a current guarantee or consensus cap. If realistic measured assumptions cannot keep the pruned-node total strictly below its target, the construction or retention model must change before activation—not silently pass the cost to hobbyists.

### 5.3 Monetary policy (provisional, governance decision required)

Recommend tail emission rather than a hard cap as a starting hypothesis, because a permanent block subsidy may provide security revenue when fees are low. Candidate parameters: 120-second block target, base unit `10^-12 RAD`, initial subsidy `S_0=10 RAD/block`, epoch `E=720` blocks, per-epoch multiplier `p/q=999525/1000000`, and tail `S_tail=0.1 RAD/block`.

Use integer-only recurrence (no floating point): `S_0 = 10·10^12` base units/block; for epoch `e≥1`, `S_e = max(S_tail, floor(S_(e−1)·999525/1000000))`, where `S_tail=0.1·10^12` base units/block. Height `h` uses epoch `e=floor(h/720)`. Block subsidy is `S_e`; a separate mint proof must prove that its output values sum exactly to `S_e + Σfees`, with no input notes and using the same output-encryption relation. Because each of the 1–16 mint outputs has a nonzero U64 value, reject totals outside `[1,16·(2^64−1)]` before proof verification; such a sum is not representable even if a verifier callback accepts it. The reward and fee total is computed from validated public transaction fees; coinbase output values remain hidden. This draft does not permit implicit burning in coinbase; any burn rule needs a public burn amount and an explicit relation. Define behavior for overflow, orphaned coinbase and genesis explicitly. This multiplier approximates a four-year half-life (about 1,460 epochs); exact emission is determined by the recurrence. The continuous approximation before the tail dominates is `S_0·H/ln(2) ≈ 15.16 million RAD`. Exact integer evaluation of this recurrence first reaches the tail at epoch 9,693 (height 6,978,960); cumulative issuance across heights 0 through 6,978,959 is 15,006,330.73651217904 RAD. This is around 13.3 years at target cadence, after which the tail adds 26,280 RAD/year at 120-second blocks. The supply is unbounded under a positive tail.

**These figures are illustrative policy proposals, not an agreed monetary commitment.** Before genesis, publish a supply/inflation simulation and evaluate miner economics, fee demand, privacy-proof block costs and wealth distribution. A tail subsidy is not a substitute for a security budget analysis.

## 6. Node, wallet, and data-availability model

- **Full validator:** verifies all consensus and proofs; keeps current output-tree and nullifier roots and enough recent data to validate new blocks. It may prune old transaction bodies only if the sync protocol and proof checkpoints let it verify current state without trusting an operator.
- **Archive node:** stores and serves all historical blocks, note ciphertexts and proof data; required for fresh bootstrap, wallet rescans and audit/replay. Archive storage has no 1 TB target and may grow without bound; the protocol must not pretend that compact proofs reconstruct those bytes.
- **Wallet:** holds spend secret `s`, KEM decapsulation key `sk_v`, scans output KEM ciphertexts, validates note commitments, tracks nullifiers and builds spend proofs. A local full node is the privacy-preserving default. Remote nodes can observe IP, timing and scan/broadcast behavior; use private transport and transaction relay, but do not claim it solves global traffic analysis.
- **Wallet recovery:** seed format must derive both spend secret and ML-KEM keypair deterministically with domain-separated KDF and exact standard keygen procedure. Derivation and backup format require independent review. A view-only wallet uses `sk_v`; it can see incoming amounts but cannot authorize spends and may not know change/outgoing balance absent exported spend metadata.
- **Pruned node:** after verifying a checkpoint/transition proof, retains a bounded recent window plus compact state and serves that window. The acceptance target is strictly less than 1 TB decimal (`10^12` bytes) of total locally retained pruned-node data over 15 years, including database/index overhead and operational headroom. This limit does not apply to archive nodes. Feasibility depends on a bounded window, compact authenticated state, checkpoint/transition proof costs, index amplification, and compaction/upgrade headroom, none of which is measured yet. This is safe only if checkpoint validity is independently consensus-authenticated and transition proofs are available. Archive providers/data-availability sampling and retention incentives remain required.
- **Data availability:** blocks containing a proof but withholding transaction ciphertexts are unacceptable: users need note data to recover and spend. Consensus must require publication of canonical block data and define peer sampling/retention. Validity is not availability. Erasure coding or sampling may help but requires a separate security analysis and enough independent peers.

Let average complete block payload be `B` bytes and target interval `T=120s`. Raw full-history growth is approximately `B·(31,557,600/T) ≈ 262,980·B` bytes/year. At target cadence, 15 years corresponds to about 3,944,700 blocks: 100 kB/block is 394.47 GB raw (before indexes/DB overhead), while every additional 1 MiB/block of proofs or other payload adds about 4.136 TB. These full-retention sensitivities are informational only; they are not an archive-size limit and do not count toward the pruned-node target. The isolated depth-64 path proof envelope has measured about 175–176 kB in one Release fixture, but the complete transaction proof and block payload are unmeasured and there are no frozen consensus block/proof byte caps. This draft therefore does **not** yet guarantee that an individual pruned node stays strictly below its 1 TB target; no archive-size target is imposed.

The in-memory reference `apply_block` API captures a bounded transfer sequence and each immutable proof-bytes reference, tallies those exact proof strings before statement serialization, and later verifies only the captured strings; this closes a mutation window between aggregate proof-size preflight and defensive snapshots. It also caps aggregate canonical transfer-statement bytes (default local setting: 1 MiB), checking the running total as bounded statements are serialized and snapshotted before any verifier callback. The individual statement that crosses the aggregate cap is serialized/parsed before its size is known; each such statement remains bounded by the codec. The full `tests/test_state.py` suite passed 25 tests in 0.10 s; it includes exact-limit cases and adversarial transfer/mint mutation checks. These are low-cost state-machine checks, not memory/CPU benchmarks or network decoder checks; both parameters are local policy, not consensus limits, and exclude other transaction fields, framing, and complete canonical block payload accounting.

For historical comparison only (not an archive requirement), a 1 TB decimal budget with database/index storage at 1.3× canonical bytes would permit about 195,004 *complete canonical block bytes per target-cadence block* (`1e12/(3,944,700·1.3)`) **if all 15 years of blocks were retained**. This is a full-retention sensitivity, not an adopted block cap and not the pruned-node budget: proof bytes, ciphertexts, headers, mint data and framing all count. The measured 175,252-byte `RDXZ64P1` path-proof envelope alone would consume about 691.3 GB raw over 15 years at one proof per target-cadence block, or about 898.7 GB after the illustrative 30% overhead multiplier, **under that full-retention assumption**. The statement-bound envelope adds statement bytes, and neither envelope is a complete transaction proof. A pruned node may discard old bodies only after an authenticated checkpoint/transition mechanism; its retained state, indices, proof/checkpoint stream, and recent-window sizes need separate measurement. PoW's 120-second target is probabilistic, not a deterministic upper bound on block count, so any strict 15-year storage bound also needs an explicit block-rate/resource argument.

A separate conditional arithmetic scenario is implemented in `radix_core/pruned_storage_model.py` and was run as a static report (not as a test or node benchmark). Its defaults assume at most 1,440 blocks/day, a 2,000,000-byte canonical block-payload cap, a 30-day retained window, 100 spends/block and 100 outputs/block, 112 bytes per nullifier/commitment-uniqueness entry with separate 1.5× index amplification assumptions for each set, 1.3× payload/database overhead, and one initial checkpoint plus an interval checkpoint for each complete or partial interval (790 records total). Under only those assumptions, now including the full-horizon commitment-uniqueness set required by ordered replay, the pruned total is 380,375,853,376 bytes (354.25 GiB), leaving 619,624,146,624 decimal bytes below the 1 TB target; the uncapped full-archive scenario is shown only for information (20,875,403,484,736 bytes, 18.99 TiB). Recent payload is 112.32 GB; historical nullifier and commitment-uniqueness state are each 132.54 GB. These are conditional arithmetic outputs, not measured storage, not enforced protocol bounds, and not a fit guarantee: the draft still has no consensus payload/block-rate caps, actual proof sizes, validated checkpoint costs, node database measurements, or peak disk-space/compaction allowance. The 15-year horizon is not a lifetime bound: current replay state copies the parent's complete nullifier and commitment-uniqueness sets and rejects duplicates against them, so both sets grow as history advances. A pruned validator cannot drop those sets unless a consensus-authenticated bounded representation preserves duplicate-rejection semantics. In particular, proof, wallet-recovery and historical data availability remain separate requirements; do not infer that a valid pruned-state estimate makes archives unnecessary.

**Proof-envelope/block-cap compatibility gap:** the current RDXL statement-bound envelope parser permits up to a 64-MiB proof payload plus a 4,096-byte statement and 18-byte header: 67,112,978 bytes before the outer transaction wrapper. The storage model's illustrative canonical block-payload cap is only 2,000,000 bytes, leaving -65,112,978 bytes of envelope-only headroom. Thus its defaults cannot admit the largest syntactically permitted RDXL envelope, even before transaction framing; the proof-envelope and block-payload limits are independent, unenforced assumptions. The proof cap is a wire maximum, not a measured/produced RDXL proof size. Under the other default storage assumptions, the solver's largest block-payload cap meeting the strict 1 TB target is 13,033,193 bytes, still 54,079,785 bytes below that maximum envelope before transaction framing. The conditional worst-case storage model therefore cannot both allow that envelope in one block and retain its strict target under these assumptions. Consensus must select compatible per-proof and per-block caps and re-evaluate storage; increasing the block cap alone worsens the worst-case retained-window estimate and is not assumed safe. The storage report now prints this envelope-only headroom and an explicit fit flag. The focused arithmetic-model suite passed 25 tests in 0.07 s, including an exact strict-target boundary where a one-byte payload cap succeeds but a target equal to its retained-window total yields no positive admissible cap; these calculations do not measure node disk use or validate the assumptions.

Under the same arithmetic scenario, categories other than the two full-horizon uniqueness sets total 115,292,013,376 bytes. Each additional assumed maximum spend/block adds 1,325,419,200 bytes of nullifier state over 15 years; each additional maximum output/block adds 1,325,419,200 bytes of commitment-uniqueness state plus 691,200 bytes of recent output indexes to the pruned model. Holding the default output cap at 100, 567 maximum spends/block yields 999,346,619,776 bytes; 568 yields 1,000,672,038,976 bytes and exceeds the target. Holding the default spend cap at 100, 567 maximum outputs/block yields 999,669,410,176 bytes; 568 yields 1,000,995,520,576 bytes. These are independent sensitivities, not recommended consensus caps; they leave virtually no safety margin, and the 2 MB block-payload cap and per-block item caps' joint feasibility is not established.

Candidate-A output records are estimated at 1,429–1,941 bytes each under the current v1 wire encoding; each includes a 1,088-byte ML-KEM ciphertext. If `Q` outputs are created per day, output-record bytes alone over 15 years are approximately `5,478.75·Q·(1,429..1,941)`, of which KEM ciphertext accounts for `5,960,880·Q` bytes. The 16-in/16-out maximum transaction statement is 32,385 bytes before its proof and block framing under the current experimental-v1 codec; the Python codec now enforces this derived cap. These costs arise from the selected wire/data-availability design, not an unavoidable rule that quantum-safe proofs must be terabytes; measure actual end-to-end proof size and verification cost before choosing the construction. If the budget fails, reduce/replace per-output payloads or proofs and revisit throughput before activation.

An archive node retains historical block bodies, ciphertexts and proofs for bootstrap, replay and wallet rescans; its full-chain storage may be much larger than 1 TB, and a proof cannot reconstruct withheld/deleted ciphertext. Output leaves and internal tree nodes can be recomputed from retained output fields, and indexes can be rebuilt. The 1 TB / 15-year planning target applies instead to the total data a lightweight individual pruned validator retains locally, including recent bodies, headers/checkpoints, authenticated current state, proofs and indexes. Its exact budget cannot be verified until state-growth, window, index-amplification and checkpoint policies are designed and measured. A pruned validator may delete local old bodies only after an independently consensus-authenticated checkpoint/transition proof and must retain sufficient authenticated root/header ancestry for anchor validation. Pruning cannot be presented as “the entire blockchain fits” or as a substitute for replicated archive/data availability. Wallet spendability also needs output ciphertexts and authenticated depth-64 inclusion paths at an accepted anchor. An uncompressed path is 64 × 64 = 4,096 bytes per retained note (about 4.10 GB for one million notes) before anchor/index/database overhead; path compression is possible but unspecified and must not be assumed in a bound. A compact append frontier preserves the current root but cannot recover arbitrary historical sibling paths; a pruned node must either retain additional path-serving data or rely on an archive/other proof-serving peer, while wallets may retain their own paths. Neither wallet witness retention nor this proof-serving service is budgeted by the current pruned-node model; `uncompressed_wallet_path_storage_bytes` reports only the raw wallet-side path payload separately, not a node-storage or complete wallet-storage bound. `uncompressed_wallet_record_and_path_bytes` additionally accepts an explicit serialized output-record size and adds one uncompressed depth-64 path per retained note: at the draft's 1,429–1,941-byte output-record range, one million notes require 5.525–6.037 GB of raw record-plus-path payload, still excluding anchors, per-note indexes, database overhead, and compression. The reference `scan_outputs_v1` accepts caller-supplied chunk/index metadata, and its cursor does not authenticate the scan source, root, or continuity.

The exploratory arithmetic model in `radix_core/pruned_storage_model.py` reports pruned-node categories separately, including full-horizon nullifier and commitment-uniqueness sets. Under its illustrative defaults (1,440 blocks/day, 2 MB block payload cap, 30-day window, 100 spends and outputs per block, 112 bytes per uniqueness entry with 1.5× index amplification, and 256 KiB per checkpoint record), it estimates 380.38 GB for the pruned node; the 20.875 TB full-archive estimate is informational only and has no target. A sensitivity scenario that substitutes one maximum-size statement-bound RDXL envelope per modeled checkpoint (64 MiB proof payload + 4 KiB statement + 18-byte envelope header) raises the pruned estimate to 438.47 GB; its corresponding archive estimate is also informational only. The exact integer solver estimates that, holding all other defaults fixed, the largest canonical block-payload cap compatible with the strict pruned target is 13,033,193 bytes; under the one-envelope-per-checkpoint sensitivity it is 11,998,767 bytes. These are policy-sizing sensitivities, not adopted or consensus-enforced caps. An earlier full Python regression run passed 152 tests, including a boundary check that the retained window cannot exceed modeled horizon blocks; the later focused 25-test run and its added exact payload-cap boundary are recorded above. This is arithmetic-model coverage, not a disk benchmark or validation of a checkpoint/transition-proof design. The per-checkpoint bound, block-rate cap, block-payload cap, per-entry costs, and database multipliers remain unverified protocol assumptions.

## 7. Threat model and security claims

Assumptions to review: ML-KEM-768 module-LWE security; collision/preimage behavior of domain-separated SHAKE256 at selected output lengths; security of the selected proof system (STARK/FRI in the quantum random-oracle model for candidate A, or the specific lattice assumptions and proof model for candidate B); AES-256-GCM confidentiality/integrity with correctly unique nonces; formal recipient/key privacy of the chosen scan protocol; correct consensus implementation; eventual data availability from enough peers; honest wallet entropy and key protection. No candidate inherits the security claims of another merely because both are described as post-quantum.

Threats addressed in principle: public chain graph analysis via hidden note membership; value disclosure; duplicate-spend/inflation; Shor attacks against EC discrete log (core candidate avoids EC); passive observer linking reused public addresses (address keys are hidden in ZK output proof, if the circuit truly hides them).

Not solved / not claimed: global P2P timing analysis, IP correlation, endpoint malware, coercion, bad randomness, denial of service, malicious node censorship, majority mining attacks, malicious software updates, quantum attacks beyond assumptions, KEM key compromise, proof-system implementation defects, supply governance failures, or guaranteed anonymity for a small anonymity set.

## 8. Major unresolved problems (must be resolved before a production spec)

1. **Proof cost:** prove ML-KEM encapsulation and AES encryption consistency, Merkle membership, hash commitments and amount balance in a transparent ZK proof. Need real benchmarks on consumer hardware; this may make the design unusable.
2. **Compact PQ scanning:** each output currently adds 1,088-byte KEM ciphertext, and wallet scans each ciphertext. Need assess CPU/storage/scan performance and whether any smaller construction preserves recipient privacy with credible PQ assumptions.
3. **Address validity and proof of possession:** define a way to prevent accidental/malicious invalid keys and safe recovery without publishing linkable keys.
4. **Nullifier data structure:** an uncompressed 512-level path has 32 KiB of 64-byte sibling digests before any sparse-tree compression; design efficient batch updates without RSA or elliptic-curve assumptions.
5. **Concrete quantum security:** calculate security after multi-target and collision attacks, STARK Fiat–Shamir in QROM, and all composed hash/KEM calls. 512-bit outputs are a proposed margin, not a finished proof.
6. **Post-quantum cryptanalysis/implementation:** independent review of ML-KEM handling, deterministic wallet derivation, proof soundness, side channels and constant-time cryptographic code.
7. **Privacy under network observation:** design and test transaction relay, wallet scanning, timing uniformity and denial-of-service protections.
8. **Consensus/economics:** select PoW, retargeting, issuance, finality assumptions and block weight based on adversarial simulation and commodity-device benchmarks.
9. **Data availability and bootstrap:** specify trust-minimized checkpoints, retention incentives and wallet restoration after years offline.
10. **Migration:** define emergency response if an assumption weakens, including proof-version activation, unspent-note migration, and rollback/reorg behavior.
11. **Memo-length metadata:** variable-length v1 exposes exact memo length through the public ciphertext size. Either accept and disclose this leakage or activate a fully specified fixed-size note-plaintext profile; padding must not be treated as an active compatibility rule until version/profile selection is unambiguous.

## 9. Implementation gates

**Gate A — formalize:** cryptographer-reviewed threat model and full relation definitions for both global-tree STARK and lattice OOM/LRS candidates; concrete hash/KEM/proof parameters; formal encodings and security assumptions. No mainnet parameters yet. Current review status and candidate relations are recorded in [Radix-Gate-A-Cryptographic-Review.md](Radix-Gate-A-Cryptographic-Review.md). This is a design-review draft, not an independent cryptographer audit; Gate A remains open pending the checklist and blockers in that document.

**Gate B — comparative prototype:** implement a minimal global-tree STARK path and a SMILE/BLOOM-based lattice OOM/LRS transaction path, plus at least one PQ recipient-discovery candidate. Create reference vectors and deterministic tests. Measure full transaction bytes, prover RAM/time, verifier time, wallet scan throughput, node sync, and worst-case validation costs on minimum-spec hardware.

**Gate C — adversarial testnet:** fuzz parsers and circuits, test nullifier races/reorgs, malformed KEM keys/ciphertexts, proof malleability, spam economics, archive outages, eclipse/traffic-analysis attacks and chain growth. Have independent teams reproduce results.

**Gate D — independent audits and public review:** at least two independent cryptographic reviews, formal security arguments, public bounty, no unresolved critical/high severity bugs. Publish parameter spreadsheets, circuit sources and reproducible binaries.

**Gate E — launch decision:** only after proof of practical performance and operational data availability. If the PQ privacy proof is too large or slow, pause/revise requirements rather than quietly fall back to ECC while marketing the system as quantum-resistant.
