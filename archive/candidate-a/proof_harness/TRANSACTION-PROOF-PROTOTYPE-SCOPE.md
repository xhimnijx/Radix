## 1. Deliberately narrow first transaction

The first target is one ordinary transfer with exactly one input note, exactly one output note, and no mint. It must reject any other input/output count. It does not cover batches, change-note policy, mint, or block/state-transition rules.

The public statement is the canonical experimental `TransactionStatementV1` serialization with:

- `chain_id: [u8; 32]`;
- version `U16LE(1)`;
- `anchor_height: u64` and `root_out: [u8; 64]` (the anchored output-tree root);
- `fee: u64`;
- exactly one 64-byte nullifier;
- exactly one canonical output record `(commitment[64], kem_ciphertext[1088], nonce[12], ciphertext[156..=668], leaf[64])`.

The current Rust 1-in/1-out codec rejects statements over 4,096 bytes and nested output records over 2,048 bytes; it canonicalizes by parse/re-encode equality. The separate Python general 1–16-in/1–16-out codec derives and enforces a 32,385-byte maximum statement before nested parsing. The experimental RDXL proof payload is capped at 64 MiB, in addition to the bounded statement and envelope header. A regression round-trips the maximum 668-byte output ciphertext with a statement within the 4,096-byte cap and rejects a correctly re-framed 669-byte ciphertext at both serializer/parser boundaries. These are parser resource limits, not recommended protocol-wide limits or chain-state budgets. Static source inspection also confirmed the Rust parser checks the 4,096-byte outer cap before frame traversal, schema-bounds nested fields before copying the ciphertext (at most 668 bytes), recomputes the output leaf, and rejects noncanonical parse/re-encode differences. No code defect was found in this pass; this is not a substitute for executing the cross-language vectors or tests.

A static audit of Python `parse_statement_v1` found that the 32,385-byte cap is checked before nested parsing; its fixed seven-field frame schema bounds top-level slices, and both vectors cap count at 16 before item appends. Nullifiers require exactly 64 bytes, each output frame is capped at `MAX_OUTPUT_FRAME_BYTES`, and nested output fields have fixed/ranged lengths. Thus network-provided lengths do not select an unbounded Python collection reservation in this path. This is a source-level bound for parser-created objects only, not a process-memory/CPU bound: the caller-owned input, Python object overhead, hashing, provider work, and any outer network buffer are excluded. `parse_address` and `parse_output_v1` likewise use fixed field schemas and reject trailing bytes, but callers must still bound/read their outer input before constructing a potentially large `bytes` object.

The public statement bytes are canonical and must be bound in full to the proof's Fiat–Shamir transcript, not merely the fields consumed by an individual AIR. For the first 1-in/1-out shape, the verifier must parse the canonical bytes, require exactly one nullifier/output, re-encode byte-for-byte, then bind every byte (and the exact byte count) as public values. The Python `radix_core.wire` codec remains the general reference (1..16 inputs/outputs); the new Rust parser is only the strict 1-in/1-out subset and must remain byte-compatible. Do not invent an alternate encoding. Lightweight tests verify borrowed exact statement/proof-slice extraction for all six statement-bound profile magics, and reject a mismatched canonical statement before deserializing deliberately invalid proof bytes; these are envelope/parser tests, not proof-generation evidence. A new Python source-shape regression also checks that RDXL reserializes and byte-compares the complete canonical statement, binds every statement byte as public values, derives output-leaf absorption blocks from the parsed output, and compares the envelope bytes before proof decoding; the complete `tests/test_proof_decoder_static_audit.py` file passed 14 tests in 0.06 s, including checks that the complete statement re-encoding is compared before the parsed `root_out` is placed first in public values, all canonical statement bytes are then appended, only the terminal level-63 path hash is bound to public root limbs, and direction selects consistent left/right inputs in byte- and bit-level Merkle hash framing, and the path-active state terminates at level 63 before entering canonical inactive level 64. Additional path-control checks pin the carry recurrence and selector gate for the seven-bit level counter, phase toggle, current/sibling/direction holds between hash boundaries, and agreement of the root selector with path deactivation. An output-leaf block-stream regression also checks zero initialization of its index outside the active stage, per-block index advancement, the public 10..14 block-count relation, and one-hot block selection. The suite also guards the dimension-derived RDXL LDE butterfly-work proxy. The balance-relation source regression also pins the output-step gate, statement fee-byte reconstruction, Boolean carry bits, per-limb carry chain, and zero boundary carries. The same static suite checks that private note bytes remain Boolean when consumed by the note hash/output cryptography, input and output amount limbs both read the note plaintext's byte-64 value field, input amount witness bits remain linked and stable across trace transitions, and Merkle current/sibling digest bits plus direction/level selectors remain Boolean. This is not Rust type-checking, proof verification, or an AIR soundness proof.

## 2. Private witness and required relation

Private input-note witness:

- `spend_secret[64]`, input ML-KEM-768 decapsulation secret key, `kem_shared_secret[32]`, `value_in: u64 > 0`, `rho_in[64]`, note randomness `[64]`, and private memo bytes of length at most 512;
- the source output record, source leaf index `u64`, and all 64 sibling digests.

Private output-note witness:

- recipient spend public component and viewing public key, encapsulation randomness/shared secret as required by the selected ML-KEM proof construction;
- `value_out: u64 > 0`, `rho_out[64]`, note randomness `[64]`, plus the plaintext/memo fields necessary to reproduce the public output ciphertext.

The composed relation must prove all of the following with common witnesses (not independent proofs that happen to have similarly named public values):

1. Prove input ML-KEM-768 decapsulation from the private viewing/decapsulation key and source KEM ciphertext; bind its result to `kem_shared_secret`.
2. Derive the Candidate-A input KDF and prove AES-256-GCM decryption of the source record yields the exact private input-note plaintext (`value_in`, `rho_in`, `randomness_in`, and memo); `owner_in` is derived separately from `pk_s` and the shared secret, then linked into the note commitment.
3. `pk_s = H_spend-pk(spend_secret)` and `owner_in = H_one-time(pk_s, kem_shared_secret)`.
4. `C_in = H_note(owner_in, value_in, rho_in, randomness_in)`.
5. Recompute the source output leaf from its canonical public fields, then fold the 64 siblings according to the 64 index bits with `H_tree-node`, obtaining the public `root_out`.
6. `nullifier = H_nullifier(spend_secret, kem_shared_secret, rho_in)` equals the single public statement nullifier.
7. For the output, prove the selected ML-KEM-768 encapsulation/decapsulation relation, derive the one-time owner and note commitment, construct the exact v1 plaintext, derive the Candidate-A KDF, and prove AES-256-GCM ciphertext/nonce/AAD equality with the public output record; recompute and bind its leaf.
8. Enforce exact-integer `value_in = value_out + fee` without overflow.

The canonical statement codec requires an output record to be internally consistent with its public leaf, but that host parser check is not a substitute for a proof relation tying the leaf, ciphertext, and hidden output opening together.

## 3. Leakage and adversary scope

Intended public leakage is exactly the canonical public statement: chain ID, version, anchor height/root, fee, nullifier, and the complete output record. Experimental-v1 ciphertext length reveals memo length (`156 + memo_length`); this prototype must explicitly admit that leakage. The single output ciphertext and KEM ciphertext are public. The relation must hide the input value, output value, spend secret, shared secret, `rho` values, note randomness, source note contents, source output fields, and Merkle path except for consequences already inferable from the public nullifier/root/statement.

The `OutputNoteOpeningV1` witness type omits `Debug` and `Clone` as defense-in-depth against accidental logging/copying; it does not protect plaintext fields from callers or process memory. Ordinary delegated proving still exposes supplied witnesses to the service, and no privacy-preserving delegation protocol is implemented; live witnesses must not be sent to an untrusted prover.

The adversary is a malicious prover choosing arbitrary witnesses and malformed/noncanonical bytes. The verifier must reject invalid proofs and malformed envelopes without crashing. The prototype will use the repository's test-only hiding PCS profile. Until a complete security analysis exists, “zero-knowledge prototype” describes the intended witness-hiding interface only—not an established ZK theorem, quantified soundness, side-channel resistance, or production/PQ security.

## 4. Proof bytes, transcript, and consensus boundary

The target full-transaction proof bytes use a distinct versioned, length-bounded envelope containing the exact canonical statement bytes and a canonical serialized proof payload. The `RDXT64P1`, `RDXS64P1`, `RDXI64P1`, `RDXJ64P1`, `RDXK64P1`, and `RDXL64P1` envelopes are separate component profiles: all bind the exact statement bytes in public values/transcript and use its `root_out`; `RDXS64P1` proves the fixed-156-byte private source record hashes to the path leaf, `RDXI64P1` adds the private input-note opening, `RDXJ64P1` additionally links private spend-secret and KEM-shared-secret inputs through the spend-pk and one-time-owner hashes into that same opening, and `RDXK64P1` adds a same-witness nullifier derivation from spend secret, KEM-shared-secret witness, and note rho. `RDXL64P1` extends RDXK with a private output-note commitment opening and exact balance against the public fee. RDXL's canonical statement parser validates the public output leaf on the host, and its current AIR also recomputes that SHAKE256 leaf from verifier-derived public absorption blocks; it now proves the output KDF and AES-256-CTR plaintext/ciphertext relation for the fixed 156-byte profile, but not output ML-KEM encapsulation, owner derivation, or GCM/GHASH tag authentication. `RDXJ64P1`, `RDXK64P1`, and `RDXL64P1` do not prove that their shared secret is an ML-KEM decapsulation. None is the complete transaction proof, and their magic/profile selection is distinct. Unknown versions, noncanonical statement encodings, noncanonical proof encodings, size overflows, truncation, trailing bytes, statement mutation, and proof mutation must fail closed; component tests exercise these cases for their envelopes.

The Rust statement codec and nullifier AIR share the named canonical nullifier-byte offset; the AIR derives its public-value position by adding the root prefix instead of duplicating a literal. The codec now also names canonical offsets for output commitment, KEM ciphertext, nonce, ciphertext-length prefix, and ciphertext bytes; RDXL derives the corresponding AIR public positions by adding the root prefix. A small regression asserts these offsets against canonical serialization at the 156-byte minimum, a middle length, and the 668-byte maximum. Formatting and compile-only `cargo check --tests` pass; the new test and all proof tests remain unexecuted. This is an auditability refactor only: serialized bytes and public-value layout are unchanged. The target prover/verifier is a research harness API only. Its exact statement-byte comparison and output-block derivation are host-side; any future production integration must route through the statement-bound RDXL verifier rather than constructing arbitrary public values or invoking a lower-level AIR verifier directly. It must not be called by `radix_core.state.apply_block()` until a complete relation and verifier exist and are explicitly injected. Consensus still checks branch-relative anchor eligibility, nullifier uniqueness, output-commitment uniqueness, ordering, and atomic state transition outside this proof unless the protocol specification deliberately moves one of those checks into the proved statement.

### Pruned-node anchor and replay contract (required, not implemented)

A membership proof only establishes that a private leaf opens against the statement's `root_out`; it does not establish that the root belongs to the active canonical branch, is inside the consensus-eligible anchor window, or that the nullifier is unused. A wallet/light client must validate the chain ID and authenticate the relevant header/checkpoint chain under its trust/finality policy, then verify that `(anchor_height, root_out)` is the branch's eligible root. The proof-verifier API must take this validated branch context rather than treating caller-supplied root bytes as trusted chain state.

A pruned node may discard historical tree leaves and spent-output paths only if it retains enough authenticated metadata to enforce the protocol rules: at minimum, a bounded table of roots for the consensus anchor window, and a durable nullifier uniqueness structure (or an explicitly specified authenticated accumulator and proof protocol). Output-commitment uniqueness needs the analogous retained index/accumulator if consensus requires it. Reorganizations must invalidate stale anchor choices and trigger revalidation before transaction acceptance. The root table's storage is `anchor_window × (height + root + required branch metadata)`; the consensus window, finality policy, accumulator design, and corresponding network encodings are not specified here, so no byte budget is claimed. This harness currently supplies none of these node/header/consensus checks.

The Python `apply_block` reference state transition now requires an explicit local `max_total_proof_bytes` policy and rejects an aggregate transfer-plus-mint proof-byte excess before statement serialization/snapshotting or verifier callbacks. This caps those proof fields only: it neither accounts for canonical transaction/block framing, outputs, or other payload bytes nor implements a protocol/consensus block cap. It is a caller-side resource guard; inputs are already materialized by the caller, and node network framing must independently bound reads. A targeted Python-source search found no `serialize_block`, `parse_block`, `BlockCodec`, or `MAX_BLOCK_PAYLOAD` implementation, so there is currently no identified place that enforces a total block-payload cap before allocation. This must be designed from a specified block wire format; do not reinterpret the proof-byte policy as a block cap. Focused pure-Python state tests cover rejection before callbacks; no STARK proving is involved.

- Cross-check every framed hash, tree fold, KEM/KDF/AEAD output, and integer sum against the Python Candidate-A vectors/reference functions.

- Reject wrong spend secret, shared secret, input/output value, `rho`, note randomness, source output, input decapsulation key, input KEM ciphertext, input nonce/ciphertext, leaf index, any sibling, anchor root, nullifier, fee, output KEM ciphertext, output nonce/ciphertext, output commitment/leaf, and canonical statement byte.

## Static PCS LDE workspace floor

The pinned Plonky3 proving path shows why raw trace size is not an adequate preflight. `amount_opening::make_config` constructs `HidingFriPcs` with four random codewords and `FriParameters::new_testing_zk`; that testing configuration sets `log_blowup = 2`. The PCS randomizes an `h × w` trace into a `2h × (w + 4)` matrix, then its coset LDE has `4 × 2h` rows. For RDXL (`h = 8,192`, `w = 14,477`), a single LDE therefore has `65,536 × 14,481` BabyBear elements: `3,796,107,264` bytes, or exactly `3,620.25 MiB` (about `3.54 GiB`) at four bytes per element. ## Bounded proof decoding and conditional allocation model (static dependency audit)

Before integrating the bounded decoder, the postcard payload-byte caps alone did not bound decoded proof-object memory. In pinned `p3-uni-stark`, `OpenedValues` contains `quotient_chunks: Vec<Vec<Challenge>>` with ordinary Serde `Vec` deserialization. The locked postcard 1.1.3 / serde_core 1.0.229 implementation caps only the initial per-vector reservation; it still appends every declared element. An empty inner `Vec` is one encoded zero-length byte, while each outer entry occupies three machine words (nominally 24 bytes on the 64-bit target). Thus a payload dominated by empty inner vectors could induce roughly 96 MiB, 384 MiB, or 1.5 GiB of outer-vector storage at the 4-, 16-, or 64-MiB wire caps, respectively, for this single vector family alone. The pinned FRI proof also contains `CommitPhaseMultiStep.sibling_values: Vec<Vec<F>>` and `BatchMultiOpening.opened_values: Vec<Vec<Vec<T>>>`, so these figures are not an aggregate upper bound. ### Bounded decoder helper (implemented and integrated; not an RSS cap)

Postcard 1.1.3 publicly exposes its Serde `Deserializer`, so a project-local wrapper can deserialize the existing `Proof<SC>` derives without vendoring Plonky3 or changing the postcard wire encoding. For a sequence whose `SeqAccess::size_hint()` is known, charge the whole declared element count before forwarding the visitor (Serde's `Vec` visitor reserves from that hint); when it is unknown, debit before each element seed is deserialized. Propagate the same budget through sequences, tuples, structs, maps, options, newtypes, enums, and tuple/struct variants; otherwise nested values can escape accounting. A separate decoded byte/string budget can be charged in byte/string visitor methods before owned visitors allocate. Use checked arithmetic and fail closed at exhaustion. The exact canonical reserialization check remains after constructing the proof.

Although current output KDF/AES-CTR constraints consume the output shared secret and bind the first 140 ciphertext bytes, the 16-byte GCM tag remains unauthenticated. That does not resolve the semantic or witness-disclosure blockers. Therefore no RDXM AIR or API is added yet, and RDXL's incomplete relation is not relabeled. Implement only as a separately versioned owner-hash-consistency profile after address semantics, KEM/shared-secret linkage, and witness-disclosure expectations are specified. The static dimension estimate remains +24 active rows and one selector column (+32 KiB raw trace), still leaving the full RDXL proving resource gate closed. ## Wallet scan resource bound (static)

The Python wallet scan helpers accept at most 1,024 output records per chunk. Each canonical record has at most 1,896 raw field bytes (`64 + 1,088 + 12 + 668 + 64`), so the maximum chunk's raw output-field payload is 1,941,504 bytes (1.8515625 MiB). The new `scan_authenticated_outputs_v1` additionally requires exactly one 64-sibling path per output; at the chunk maximum, those sibling digests total 4,194,304 raw bytes (4 MiB), or 6,135,808 raw bytes combined with output fields. This permits up to 65,536 depth-level hash steps per full chunk; no full-chunk time measurement is claimed. Paths and output records are validated/snapshotted before provider callbacks, and authenticated scanning uses the same detached record snapshots for root membership and recovery to avoid a post-authentication mutation window. `WalletScanCursorV1` tracks local positions and locks to legacy or authenticated mode after its first successful chunk, preventing caller-asserted legacy history from silently becoming authenticated history (or vice versa). In authenticated mode, the cursor also pins the exact caller-supplied root/optional leaf-count pair; later checkpoint changes are rejected. Mode/checkpoint pinning and advancement happen only after the chunk succeeds. `snapshot()` and `from_snapshot()` provide a validated immutable state object for caller-managed persistence. `WalletScanCursorSnapshotV1` now has a strict `RDXWCS01` canonical codec (19-92 bytes) with 65-bit little-endian index/count fields, explicit mode/count flags, exact-length parsing, and no trailing bytes. This is local persistence only: decoding does not authenticate scan history, root/count, or source. A snapshot remains unavailable during an active scan. Use a new cursor for a different mode or checkpoint. These local locks prevent accidental history/checkpoint mixing; they do not authenticate the root/header, prove requested-range completeness, or provide source/continuity semantics. A static audit found that a non-bytes root object could otherwise reach checkpoint tuple comparison while the lock was held; `scan_authenticated_chunk` now validates exact bytes/int checkpoint components before `_scan_chunk` acquires the lock, preventing caller-defined equality code there. `EqualityBomb` regressions now cover both root and leaf-count values; tests were not run this round. A caller may pass `trusted_leaf_count` to reject a supplied range beyond the populated prefix; it must be authenticated for the same root/checkpoint. This optional bound does not prove range completeness. Raw field/path totals are bounded input-byte estimates, not total heap/working-set bounds: Python tuple/object overhead, caller-owned records/path tuples, KEM/GCM workspaces, hash temporaries, and provider/runtime allocations are excluded. Scan CPU/peak memory have not been measured on desktop or mobile, so these limits alone do not establish full wallet-scan fit within either device budget.

Provider trust and scan privacy remain explicit limits: the caller-supplied KEM adapter receives raw decapsulation-key bytes and each output ciphertext; the AEAD adapter receives shared keys/ciphertexts and its decrypt result includes plaintext or an authentication rejection. Remote or logging adapters can therefore steal wallet secrets, correlate scans, and learn matches and timing. The interfaces specify no remote isolation, padding/batching privacy, or traffic-metadata protection. The provider and wallet API documentation now warns that adapters are trusted local key boundaries; no cryptographic privacy protocol is claimed.

The local cursor snapshot format now has focused codec coverage: `python -m pytest -q tests/test_wallet.py -k "snapshot_encoding or wallet_cursor"` passed (**7 passed, 25 deselected in 0.17 s**). It round-trips fresh, legacy, authenticated, and 65-bit boundary states, and rejects malformed versions/flags, truncation, extra bytes, non-byte input, and out-of-range indices/counts. The codec itself is bounded and canonical but does not turn a caller-managed snapshot into an authenticated checkpoint. `WalletScanCursorV1.from_authenticated_snapshot_bytes` now offers a safer restore path: callers must supply an independently trusted root, authenticated leaf count, and expected next output index, and the API rejects mismatches or legacy-mode state before restoring. Focused regression coverage passed (**6 passed, 27 deselected in 0.19 s**), including mismatched root/count/position, legacy state, and index/count inconsistency. The expected index and checkpoint still need an independent trusted source; this does not authenticate prior scan completeness or continuity.

## Current gap

The harness has separate public-balance, demo amount-opening, spend-key-hash, one-time-owner-hash, note-commitment-hash, nullifier-hash, and single-tree-node-hash proofs, plus an independent-proof bundle linking only a common public spend key. It also has linked depth-2 and depth-64 path AIRs. The root-only `RDXZ64P1` proves private depth-64 membership against a caller-supplied root. `RDXT64P1` binds the exact canonical 1-in/1-out statement bytes into public values/transcript but retains arbitrary-private-leaf semantics. `RDXS64P1` hashes a private fixed-156-byte canonical source `OutputRecordV1` in the AIR, links its private digest to the path, and binds the path root to statement `root_out`. `RDXI64P1` additionally proves a private note opening matches the commitment in that private source record, in the same AIR as source hash and path. `RDXJ64P1` additionally composes the spend-secret hash and one-time-owner hash so the derived owner is the owner in that same note opening. `RDXK64P1` extends that relation with a nullifier derived from the same private spend secret, KEM-shared-secret witness, and rho and binds the result to the public statement. `RDXL64P1` adds a private output-note opening and exact output-plus-fee balance. It does not prove input ML-KEM decapsulation or GCM/GHASH tag authentication, nor output ML-KEM encapsulation or output-owner derivation; RDXL does constrain the output KDF and the first 140 output ciphertext bytes through AES-256-CTR to the private output-note plaintext, while leaving GCM/GHASH tag authentication unproved. `RDXJ64P1`, `RDXK64P1`, and `RDXL64P1` do not prove ML-KEM decapsulation. Fixed-length source profiles reject 155- and 157-byte ciphertexts; variable-length source ciphertexts are not supported.
