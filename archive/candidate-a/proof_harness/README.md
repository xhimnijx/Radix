# Candidate-A STARK component harness (research only)

This isolated crate is a **component feasibility experiment**, not a Radix transaction-proof implementation and not a consensus verifier. It contains independent proof components for public bounded balance, a demo Poseidon2 amount opening, Candidate-A SHAKE256 spend-key/owner/note/nullifier/tree-node hash openings, linked depth-2 and depth-64 path relations, optional owner-proof bundles, and experimental single-AIR compositions through `RDXL64P1`. No profile verifies a complete Radix transaction or is suitable for consensus.

Five standalone Candidate-A SHAKE256 hash openings are tested: spend-public-key, one-time owner, note commitment, nullifier, and tree-node. The linked depth-2/depth-64 path AIRs and statement-bound `RDXT64P1` remain path subrelations; `RDXT64P1` still uses an arbitrary private leaf and does not link it to the source output or nullifier. The experimental `RDXK64P1` profile composes spend-key and one-time-owner hashes, the private note opening, fixed-156-byte source output, depth-64 path, and nullifier derivation in one AIR using the same private spend secret, KEM shared-secret witness, and note rho; its digest is bound to the canonical public statement. It does not prove ML-KEM decapsulation, output KEM/AEAD, value balance, multi-note sums, mint, or state-transition rules. The optional owner bundle still verifies independent proofs with a common public `pk_s`, not common hidden witnesses. The Rust statement codec by itself remains host-side parsing and output-leaf hash checking, not an AIR relation. No proof from this harness is accepted by `radix_core.state.apply_block()`; that boundary remains fail-closed and requires an injected full transaction verifier.

The broader 1-input/1-output transaction target, including the public statement, private witness, leakage, required common-witness relations, and adversarial acceptance tests, is specified in [TRANSACTION-PROOF-PROTOTYPE-SCOPE.md](TRANSACTION-PROOF-PROTOTYPE-SCOPE.md). The supplied Akita paper's possible PCS benefits and the invalid direct BabyBear ring-switch proposal are reviewed in [AKITA-RING-SWITCH-COMPATIBILITY.md](AKITA-RING-SWITCH-COMPATIBILITY.md). The canonical Rust codec is implemented as a host-side building block. Experimental `RDXI64P1` composes the private note opening, fixed-156-byte source output, and depth-64 path; `RDXJ64P1` adds spend-key and one-time-owner derivation; `RDXK64P1` further adds a same-witness nullifier derivation and public-digest binding; `RDXL64P1` retains canonical statement binding (its root public input comes only from the parsed statement, not a separate caller argument) and adds an output-note opening, exact one-input/one-output-plus-fee balance, and output KDF/AES-CTR constraints for the fixed empty-memo profile's first 140 ciphertext bytes. Its output owner is still a free witness, not derived from recipient keys. These are research component profiles, not the complete transaction relation or verifier.

## Reproducible proof experiment

- Backend: Plonky3 `p3-uni-stark` / univariate STARK with `TwoAdicFriPcs`.
- Source pin: commit `fe5e46d755b8a7d9069778361e21b33e5978b377`; all Plonky3 crate dependencies use this exact `rev` and the generated `Cargo.lock` must be checked in.
- Base field: BabyBear; challenge field: `BinomialExtensionField<BabyBear, 4>`.
- Trace layout: 64 identical rows, 197 columns (192 bit-decomposition columns and 5 carry columns); AIR maximum constraint degree 2.
- PCS/hash stack: `Radix2DitParallel<BabyBear>` and `TwoAdicFriPcs`; `ValMmcs = MerkleTreeMmcs<BabyBear::Packing, BabyBear::Packing, PaddingFreeSponge<Poseidon2BabyBear<16>,16,8,8>, TruncatedPermutation<Poseidon2BabyBear<16>,2,8,16>,2,8>` initialized with shift `0`; challenge MMCS is `ExtensionMmcs<BabyBear, BinomialExtensionField<BabyBear,4>, ValMmcs>`. The transcript challenger is `DuplexChallenger<BabyBear, Poseidon2BabyBear<16>,16,8>`.
- FRI test profile: `log_blowup=4`, `log_final_poly_len=0`, `max_log_arity=1`, `num_queries=32`, batch/commit/query proof-of-work bits all 0. STARK lookup and OOD proof-of-work bits are 0.
- Configuration randomness: deterministic `SmallRng` seed `0x5241_4449_585f_4150` for reproducible experimental Poseidon2 parameters. This is not a production parameter-generation procedure.
- **No numeric soundness-bit claim is made.** These are test parameters only. No complete `StarkSecurityParams`/`ProvenSecurity` calculation or full theorem-premise audit has been performed. Do not derive Radix security from `log_blowup × num_queries`, test success, or this component result.

The harness envelope (`RDXCMP01`, version 1) canonically encodes the 24-byte public component statement and a length-delimited postcard proof payload. The verifier rejects unknown versions, incorrect lengths, trailing data, non-canonical proof serialization, unbalanced public values, and backend verification failures. The pinned upstream documentation warns that malformed proofs may panic in some code paths, so verifier calls are wrapped in `catch_unwind` and panics become an error result. Plonky3's Fiat–Shamir transcript binds its public values for this component. This envelope is **not** the encoding or transcript of a Radix transaction proof.

## Build and run

From this directory, with Rust/Cargo installed:

```powershell
cargo test --locked
cargo run --release -- 1200 1100 100
```

The arguments are public input total, public output total, and public fee. The defaults are the same valid example. A failed/overflowing balance is rejected. The sample `1200 1100 100` currently produces and verifies a 53,349-byte envelope under this pinned profile; this is a single component measurement, not a size estimate for a Radix transaction proof.

For a side-effect-free dimension estimate of the current RDXL trace, ZK-randomized trace, and PCS LDE payloads, run `cargo run --release -- rdxl-resource-report`. This prints raw matrix sizes, compares the LDE payload alone to the provisional 4-GiB desktop / 1-GiB mobile process caps, and reports the randomized-matrix-plus-LDE payload sum as a hypothetical coexistence case. That sum exceeds the desktop cap before any other allocations; actual overlap and peak RSS remain unmeasured. The command does not build a proof trace or run a test, and this report is not evidence that proving fits either device budget. The RDXL proving entry-point preflight uses the smaller 1-GiB mobile cap for both targets because there is no target-specific runtime resource policy; it is a raw-payload guard, not fit evidence.

## Local parallel proving experiment

**Conservative resource defaults:** the `parallel` feature is now opt-in (default features are empty). `.cargo/config.toml` also limits Cargo build jobs, Rust test threads, and Rayon workers to one unless explicitly overridden by the caller. Seven depth-64 proof roundtrip/adversarial tests—including the RDXL test—are marked ignored because they allocate and scan large traces and invoke full STARK proving. Do not opt them in until the target machine's available RAM and safe limits are established. The older parallel timings below predate RDXL and are not a recommendation to increase workers on a memory-limited host.

A depth-64 proof-only benchmark on one Intel Core i7-1185G7 host (4 cores/8 threads) measured the Release prove call at 44.40 s with Rayon capped at 1 thread; two 4-thread runs were 20.80 s and 22.09 s (median 21.44 s); two 8-thread runs were 13.58 s and 17.35 s (median 15.47 s). A prior non-parallel single sample was 41.24 s. This suggests roughly 2.7× improvement at 8 threads for this fixture, but the two-run samples vary and are not a general performance guarantee. Per-run verify samples were about 24–27 ms; proof envelopes were about 175–176 kB. A separate direct `p3-util/parallel` trial showed no clear gain in one run and was not retained.

A 100 ms polling sample in the earlier isolated Merkle-path experiment observed about 2.49 GiB (2.54 GB) peak working set at 1, 4, and 8 threads. This was an approximate per-process sample, not a reliable worst-case RAM bound; it predates the larger composed AIRs. The current RDXL trace is 8,192 × 14,477 BabyBear values (474,382,336 B, about 452.4 MiB for the trace alone, before proving workspace), calculated from the current trace dimensions. The earlier row-count, constraint-count, and AIR-scan upper-bound estimates in this paragraph are stale after the relation expansion and are not resource estimates for current RDXL. The current RDXL peak remains unknown; no full proving benchmark has been run. The four mutation scans now reuse the same trace. The RDXL source/key/note/nullifier builder allocates the final 8,192-row, 14,477-column matrix once; output composition fills the upper-half rows in place rather than first holding a separate 4,096-row full-width matrix and then allocating/copying into the final matrix. At the former expansion point, those two full-width buffers were 226.203 MiB and 452.406 MiB respectively after the disjoint-row AES S-box column overlays. The edit removes the former intermediate at that point, but allocates the final matrix earlier while the narrower source-note trace is live; do not treat 226.203 MiB as net peak/RSS savings. This is an allocation-overlap reduction only; before/after whole-process peaks remain unmeasured. The builder also carries the spend-secret and input shared-secret byte/bit witnesses through all 8,192 rows, matching the AIR's full-trace transition constraints; this static consistency fix has not yet been AIR-checked. Temporary note and base traces are dropped promptly. These are structural allocation/copy reductions, not measured speedups. Setting `RDXL_PROFILE_TIMINGS=1` on a focused RDXL prove call emits preflight, input/output note, path/base trace, output trace, STARK prove, envelope-encode, and total elapsed times plus raw trace bytes; it does not measure peak process memory or log witness values. Use an external process sampler for peak working set/private bytes, and establish a conservative machine-specific RAM budget before opting in to any ignored full proof test. The old isolated-path measurement is not an RDXL memory estimate.

## Average-device readiness gate (provisional)

“Average computer/mobile” is not a uniform hardware specification. For planning only, use an 8-GiB laptop and a 4-GiB phone as conservative reference classes; require the complete relevant test/proof workload to stay below 4 GiB process working set on the laptop and 1 GiB app working set on the phone, leaving room for the OS and other apps. These are provisional gates, not measured platform guarantees; replace them if the intended device class is different. Historical composed-proof test runs sampled about 5.74 GiB (RDXS), 7.73 GiB (RDXI), and 9.22 GiB (RDXJ) of process working set, exceeding the provisional laptop gate.

The corrected `rdxl-resource-report` dimension calculation is more informative than the raw trace size alone: the pinned Keccak AIR has 2,937 columns, yielding an RDXL width of 14,477 after reusing disjoint-row AES S-box input, output, and witness columns; the trace payload is 474,382,336 B (452.40625 MiB), the randomized matrix is 949,026,816 B (905.0625 MiB), and the PCS LDE payload is 3,796,107,264 B (3,620.25 MiB). The LDE payload alone exceeds the 1-GiB mobile app cap by 2,596.25 MiB and is about 88.5% of the 4-GiB laptop process cap. The randomized-matrix-plus-LDE hypothetical coexistence sum is 4,745,134,080 B (4,525.3125 MiB), exceeding the 4-GiB laptop process cap by 429.3125 MiB. These are dimension-derived payloads, not observed peaks or complete peak bounds: buffer overlap, trace retention, other prover workspaces, allocator overhead, peak RSS, and end-to-end RDXL proving/verification time remain unmeasured. No mobile build or wallet scan/keygen/Scrypt resource measurement exists. Thus full RDXL proving is not established to fit either reference budget; keep the ignored heavy tests deferred. Do not reduce soundness, privacy, or cryptographic strength merely to fit these limits.

## Process-memory sampling helper

`sample_process_memory.ps1` attaches to one already-running process ID and writes timestamped working-set and private-byte samples to a new CSV file. It does not launch or stop the target, enforce a RAM ceiling, or include child processes or whole-machine use. Sampling is periodic, so peaks between samples can be missed; attaching after proving begins can also miss an early peak. The output path must not already exist. For a future explicitly authorized, RAM-budgeted run, identify the Rust test process in another PowerShell window and start sampling before its proving phase:

```powershell
Get-Process | Where-Object ProcessName -like 'radix_proof_harness-*' | Select-Object Id, ProcessName
$targetPid = [int](Read-Host 'Enter the Rust test process ID')
$csvPath = Join-Path $env:TEMP ('rdxl-process-memory-{0}.csv' -f [guid]::NewGuid().ToString('N'))
.\sample_process_memory.ps1 -ProcessId $targetPid -CsvPath $csvPath -IntervalMilliseconds 250 -MaxDurationSeconds 1800
```

This helper is a measurement aid, not a safety bound. RDXL proving remains deferred until a machine-specific RAM ceiling is established and explicitly authorized.

CLI input files are read through a `take(limit + 1)` cap before parsing: fixed-format openings are limited to 4,168 bytes, expected roots to 64 bytes, and each proof/bundle file to its codec-derived maximum envelope. The largest CLI proof is the depth-64 path envelope (64 MiB payload + 78-byte header); the owner bundle is capped at 32 MiB + 146-byte header, while other profiles have 4- or 16-MiB payload caps plus their headers. This prevents unbounded file-read allocation and avoids applying a loose global cap to smaller profiles, but does not bound decoded proof-object RSS or prove device fit; those remain resource-gate concerns.

## Proving delegation, privacy, and fees

Ordinary outsourced proving exposes the prover's witness. For a real transaction that could include the spend secret, KEM shared secret, note randomness, and Merkle siblings, so sending a live witness to a miner or proving service is not a safe default; encrypting the connection does not hide the witness from the service endpoint. A miner can verify an already completed proof without receiving that witness. The transaction fee normally rewards inclusion to the block producer; it does not automatically compensate a separate proving service. A proving-service reward would need an explicit separate payment or protocol fee split. For this prototype, prefer local proving or an explicitly trusted optional service with disposable test keys; privacy-preserving delegation (for example MPC) is a separate protocol design, not a drop-in optimization. The `OutputNoteOpeningV1` witness type intentionally omits `Debug` and `Clone` to discourage accidental log disclosure and easy duplication, but this is only defense-in-depth: its fields remain ordinary in-process plaintext and callers can still copy or print them manually.

## Experimental ZK amount-opening subrelation (`RDXZAM01`)

This second component proves knowledge of a private non-zero `u64` amount and a BabyBear field blinding value whose test-only Poseidon2 output equals the public commitment `C`. The AIR splits the amount into four 16-bit limbs, constrains every bit and the nonzero condition, supplies the limbs/blinding/fixed domain tag as Poseidon2 input lanes, and explicitly constrains the final permutation output to the public value. The public statement is just the canonical 32-bit BabyBear commitment; the domain tag and envelope version are fixed by this prototype profile. This is an opening/range subrelation only—not balance, ownership, Merkle membership, nullifier correctness, KEM/AEAD, or a complete transfer.

- Commitment hash: pinned Plonky3 `Poseidon2Air` over BabyBear, with a fixed domain tag. It is a **test-only substitute**, not Candidate-A's SHAKE256 framing/hash or an implementation of its note commitment.
- Proof system: `HidingFriPcs` with `MerkleTreeHidingMmcs`, four random codewords, and `FriParameters::new_testing_zk`. The amount trace has 128 rows; prover/MMCS randomness and the amount blinding are seeded from the OS via the rand thread RNG into `StdRng`. The ZK PCS's hiding budget is checked by the backend at proof time. The verifier is kept behind `catch_unwind` because pinned upstream documentation does not guarantee malformed-proof panic-freedom.
- Envelope/transcript: versioned `RDXZAM01` envelope = 8-byte magic, little-endian `u16` version, canonical little-endian `u32` commitment, little-endian `u32` proof length, then canonical postcard-serialized Plonky3 proof bytes. Fiat–Shamir transcript verification binds the one public commitment. This is a component envelope, not the Radix canonical wire format or a full transaction transcript.
- Leakage and security: the public commitment and proof length are visible. BabyBear is only about 31 bits, so this demo commitment is **not a cryptographically adequate hiding/binding commitment**; do not claim confidential amount security from it. The proof backend is configured for ZK so its trace is hidden beyond the public statement under the PCS assumptions, but this does not repair weak statement-level commitment privacy, provide a quantified soundness bound, or establish post-quantum security. The FRI profile is testing-only; no numeric security claim is made.
- Adversarial tests cover a valid `u64` opening, changed public commitment, mutated proof bytes, zero amount, and truncated/trailing/wrong-magic envelopes. Repeated proofs for the same opening verify but differ due to fresh PCS randomness.
- CLI: `cargo run --release -- amount-prove <private-amount-u64> <proof-file>` writes a proof envelope; `cargo run --release -- amount-verify <proof-file>` verifies it and displays the public commitment. The amount supplied on the prover command line is visible to that machine's shell/process environment; use the Rust API directly if that local operational leakage is undesirable.

This amount module is intentionally detached from `radix_core.state.apply_block()` and from `TransferVerifier`. **Do not use its verifier as a transaction authorization callback.**

## Candidate-A `H_spend-pk` hash-opening subrelation (`RDXZSK01`)

This third component proves knowledge of a private 64-byte secret `s` such that the public 64-byte key equals `SHAKE256(Frame("radix/spend-pk/v1", [s]), 64)`. Its 95-byte frame uses the Candidate-A `RADIX` v1 framing: tag `radix/spend-pk/v1`, one argument, and a four-byte little-endian length of 64. The wrapper applies SHAKE256's 136-byte rate, little-endian lane absorption, `0x1f` domain suffix, final `0x80` pad bit, and binds the first 64 squeezed bytes to the public key. A known-answer regression uses the existing Python Candidate-A vector for `bytes(range(64))`.

- Backend: pinned Plonky3 `p3-keccak-air` Keccak-f AIR embedded through `SubAirBuilder`; the wrapper supplies the constraints that the permutation AIR does not: secret byte range checks, exact frame bytes, capacity zeroing, SHAKE padding, and digest binding. The pinned Keccak-f AIR by itself is **not** SHAKE256.
- The experimental trace has 128 rows and 3,513 columns at the pinned revision (2,937 Keccak AIR columns plus 576 secret-byte/bit witness columns). It includes five complete identical permutations and eight rows of a sixth partial permutation to fit the existing testing-only hiding-PCS profile. Outputs of completed permutations are bound to the same public digest. This is an implementation detail of the prototype, not a protocol-level optimization or a security claim.
- Public statement: the 64-byte `pk_s`. Envelope: versioned `RDXZSK01` magic, little-endian `u16` version, 64 public key bytes, little-endian `u32` proof length, and canonical postcard proof bytes. This envelope/transcript is **not** Radix canonical transaction wire or a transaction transcript.
- The proof is only for the one-block `H_spend-pk` relation at this fixed input length. It does not prove that the secret is authorized for any note, that a note is in the tree, or that any transaction is valid. No numeric soundness, production zero-knowledge, PQ-security, or end-to-end security claim is made; the existing FRI profile is testing-only, and independent cryptographic review has not been performed.
- Adversarial tests alter the public key and proof bytes and add trailing data; verification rejects them. Envelope decoding is canonical and bounded, and pinned verifier panics are caught.
- CLI: `cargo run --release -- spend-pk-prove <secret-file-64-bytes> <proof-file>` reads the secret from an exact 64-byte file (rather than a command-line argument) and writes the proof. `cargo run --release -- spend-pk-verify <proof-file>` verifies it and prints the public key. The secret file, shell process, memory, and local machine remain within the caller's trust boundary; this is not secure secret handling.

This hash-opening module is intentionally detached from `radix_core.state.apply_block()` and from `TransferVerifier`. **Do not use its verifier as a transaction authorization callback.**

## Candidate-A `H_one-time` owner-hash subrelation (`RDXZOW01`)

This fourth component proves knowledge of a private 32-byte shared secret `ss` such that `owner = SHAKE256(Frame("radix/one-time/v1", [pk_s, ss]), 64)`. The frame is 131 bytes: Candidate-A `RADIX` v1 metadata, a 64-byte public spend key, and a 32-byte secret field. The AIR applies a one-block 136-byte SHAKE256 rate block with suffix `0x1f` at byte 131 and final `0x80` at byte 135, little-endian lane absorption, zero capacity, and output binding. Its Rust known-answer test matches the Python Candidate-A implementation for `pk_s = bytes(range(64))` and `ss = bytes(range(32))`.

- Backend and trace: same pinned `p3-keccak-air` Keccak-f AIR plus explicit frame/sponge constraints. The trace is 128 rows and 3,225 columns at the pinned revision (2,937 Keccak columns plus 288 secret-byte/bit witness columns); it uses five complete identical permutations plus eight partial rows to fit the testing-only hiding profile. All complete outputs bind to one public owner digest.
- Public statement: raw `pk_s` (64 bytes) and `owner` (64 bytes). Versioned `RDXZOW01` envelope: magic, little-endian `u16` version, those 128 statement bytes, little-endian `u32` proof length, canonical postcard proof. This is a prototype component envelope, not transaction wire or a shared transaction transcript.
- Adversarial test changes the public key, owner, proof bytes, and envelope length; verification rejects. The proof does **not** establish that `ss` is the result of ML-KEM-768 decapsulation, bind to a ciphertext, prove a Merkle path, or compose with the spend-key hash proof.
- CLI: `cargo run --release -- note-owner-prove <spend-pk-file-64-bytes> <shared-secret-file-32-bytes> <proof-file>` and `cargo run --release -- note-owner-verify <proof-file>`. The proof-producing CLI reads private bytes from files, but files/process memory are not secure secret handling.
- As with the spend-key component, no numeric soundness, production zero-knowledge, PQ-security, or end-to-end security claim is made; this stays detached from `radix_core.state.apply_block()` and `TransferVerifier`.

## Linked owner-hash proof bundle (`RDXBND01`)

This wrapper creates one spend-key hash proof and one one-time owner hash proof, then packages them with the public `(pk_s, owner)` pair. The verifier independently verifies both child envelopes and rejects unless both bind the same `pk_s` and the owner proof matches the bundle's public owner. Its fixed envelope is `RDXBND01`, little-endian `u16` version, 64-byte `pk_s`, 64-byte owner, little-endian `u32` child lengths, then the two exact child envelopes. Each child is independently bounded and verified.

This is conjunction by packaging, not a jointly composed STARK: each child has a separate Fiat–Shamir transcript; the bundle adds no shared transcript or transaction statement. It proves knowledge of a spend secret and a shared secret for the two fixed hashes under the prototype proofs' assumptions, with a public key link. It still does not show that the shared secret is an ML-KEM result, tie an encapsulation to a note, prove Merkle membership, or establish a valid Radix transfer. The `owner-binding-prove <spend-secret-file-64-bytes> <shared-secret-file-32-bytes> <bundle-file>` and `owner-binding-verify <bundle-file>` CLI commands expose the linked bundle; secret files/process memory remain in the caller's trust boundary.

## Candidate-A two-block note-commitment opening (`RDXZNC01`)

This component proves knowledge of `(owner: [u8;64], value: u64, rho: [u8;64], randomness: [u8;64])`, with `value != 0`, such that the public 64-byte digest is exactly `SHAKE256(Frame("radix/note/v1", [owner, U64LE(value), rho, randomness]), 64)`. The canonical frame is 239 bytes: the three 64-byte fields and an eight-byte little-endian value are each length-prefixed with `U32`. Thus the 136-byte SHAKE rate absorbs two blocks; the `0x1f` suffix is at global byte 239 and the final `0x80` bit is at global byte 271. The relation proves only the hash opening and U64 representation, not the provenance/ownership of `owner` or any transaction semantics.

- Backend/wrapper: pinned `p3-keccak-air::KeccakAir` for Keccak-f plus explicit phase alternation, private-byte range checks, nonzero value constraint, exact frame, zero initial capacity, a bit-constrained 1600-bit XOR state transition between the first and second rate blocks, SHAKE padding, and public digest binding. The wrapper independently binds each second-block absorption to the prior first-block permutation output; the base Keccak AIR alone would not prove a two-block SHAKE hash.
- Trace: 128 rows and 6,035 columns at the pinned revision. It contains five complete permutations and eight rows of a sixth; first/second absorption phases alternate. Trace size and the existing hidden testing FRI profile are experimental implementation parameters, not a protocol or security claim.
- Public statement/envelope: only the commitment digest is public. `RDXZNC01` version 1 contains the 64-byte digest followed by a bounded length and canonical postcard proof. The envelope is neither Radix transaction wire nor a transaction transcript.
- Tests: the Rust proof matches the Candidate-A Python known-answer commitment; tests alter statement and proof bytes, magic/version, length, and phase classification. Zero-value proving is rejected. The adversarial phase-substitution test confirms a mislabelled second-absorption trace is rejected by the proof/verification boundary.
- CLI: `cargo run --release -- note-commitment-prove <opening-file-200-bytes> <proof-file>` reads `owner64 || value-u64-le || rho64 || randomness64`; `note-commitment-verify <proof-file>` verifies and prints the digest. Secret files, process memory, and local host remain in the caller's trust boundary.
- This is an isolated hash-opening experiment, not a full note/transfer proof. It is detached from `radix_core.state.apply_block()` and `TransferVerifier`. No production zero-knowledge, numeric soundness, post-quantum security, or end-to-end claim is made.

## Candidate-A two-block tree-node hash opening (`RDXZTN01`)

This component proves knowledge of `(left: [u8;64], right: [u8;64])` for one public tree level `0..63` and public parent digest `SHAKE256(Frame("radix/tree-node/v1", [level-u8, left, right]), 64)`. The canonical frame is 169 bytes: a `RADIX` v1 header, three length-prefixed fields with lengths 1/64/64, and 64-byte children. SHAKE padding places `0x1f` at global byte 169 and the final `0x80` bit at byte 271. The left/right child digests are private in this standalone proof; level and parent are public.

- Backend/wrapper: pinned Keccak AIR with private-byte range checks, exact frame and padding, zero capacity, phase alternation, constrained two-block absorption, and public level/parent binding.
- Public envelope: `RDXZTN01` version 1 contains one level byte, the 64-byte parent, a bounded proof length, and canonical postcard proof bytes.
- Tests: known-answer vector cross-checked against `radix_core.crypto.shake_frame`, child-preimage mutation, phase substitution, level and digest statement mutations, envelope tampering, and out-of-range levels.
- CLI: `cargo run --release -- tree-node-prove <opening-file-129-bytes> <proof-file>` reads `level-u8 || left64 || right64`; `tree-node-verify <proof-file>` verifies and prints public level/parent.
- This is one node-hash opening, not a Merkle membership/path proof. It does not constrain index-bit orientation, link adjacent tree levels, bind a note leaf or transaction root, or prove transaction validity. Not wired to consensus or `TransferVerifier`.

## Linked Candidate-A two-level path opening (`RDXZ2P01`)

This separate AIR proves one exact linked relation: `child = H_tree-node(0, ordered(leaf, sibling0))`, followed by `root = H_tree-node(1, ordered(child, sibling1))`. The two private direction bits select left/right order. The intermediate digest is constrained in the same AIR and is not supplied as a freely chosen public value. The public root is included in the proof statement and the verifier must independently supply the expected 64-byte root.

- Trace: 128 rows and 5,390 columns at the pinned revision; five complete Keccak permutations and an eight-row partial continuation, with stage/phase schedule, private byte/bit constraints, inter-node digest link, and root binding. This schedule covers exactly two tree levels; it is not the depth-64 proof described below.
- Envelope: `RDXZ2P01`, version 1, public 64-byte root, bounded proof length, and canonical postcard proof bytes. Proving rejects a witness whose computed root differs from the caller's expected root; verifying also compares the envelope root to an externally supplied expected root.
- Tests: fixed two-level vector is cross-checked against the standalone level-0 node proof; the linked proof is proved/verified; wrong expected roots, changed siblings, direction substitutions, tampered proof payload bytes, malformed magic, truncation, and trailing envelope data are rejected. This validates only the linked depth-2 relation.
- CLI: `two-level-path-prove <opening-file-194-bytes> <expected-root-file-64-bytes> <proof-file>` reads `leaf64 || sibling0-64 || sibling1-64 || direction0-u8 || direction1-u8` (directions must be 0 or 1); `two-level-path-verify <proof-file> <expected-root-file-64-bytes>` verifies against the caller-provided root. Private input files/process memory are not secure secret handling.
- This prototype does not prove depth-64 membership, leaf construction, an index or index-bit/path orientation across 64 levels, canonical transaction statement binding, transaction validity, or consensus acceptance. No production ZK, quantified soundness, post-quantum, or transaction-level security claim is made.

## Experimental linked Candidate-A depth-64 path (`RDXZ64P1`)

A separate AIR links exactly 64 framed tree-node hashes in one proof. Its private witness is `leaf64 || sibling[64] || path_index_u64`; path bit `i` chooses the left/right ordering at level `i`, and the hash frame's level byte is constrained to 0 through 63. The sole public statement is the expected 64-byte root; the verifier supplies that root independently. The linked prove/verify test now passes in the pinned harness. This is a path-relation prototype, not a transaction proof.

- Trace layout: 4,096 rows × 3,955 columns; 128 active Keccak permutations (two per Merkle node), or 3,072 active round rows. The Keccak trace helper pads those rows to the next power of two without adding dummy permutations. Digest witnesses use Boolean bit columns directly, removing redundant per-byte columns; the second absorption block uses 288 selected output bits rather than a full output-bit matrix. These are source-layout counts, not measured proving-memory or runtime claims.
- Envelope: `RDXZ64P1`, version 1, public 64-byte root, length-delimited canonical postcard proof, maximum 64 MiB. The opening file for the CLI is exactly 4,168 bytes: `leaf64 || 64 sibling digests (level order) || little-endian path_index_u64`. The index is private to the proof.
- CLI: `depth64-path-prove <opening-file-4168-bytes> <expected-root-file-64-bytes> <proof-file>` and `depth64-path-verify <proof-file> <expected-root-file-64-bytes>`. The private opening file/process memory are not secure secret handling.
- Tests: the linked depth-64 prove/verify test passes, including wrong expected root, changed sibling/index, malformed magic/version/length, trailing/truncated envelope bytes, and tampered proof payload; a separate root-only test matches the Python reference. On an Intel Core i7-1185G7 (4 cores/8 threads), the Release test emitted a 175,252-byte proof envelope, took 41.236 s for `prove_depth64_path` (including trace construction), and 18.783 ms for `verify_depth64_path`. This is the prior non-parallel single fixture on one host, not a benchmark distribution; peak RAM was not measured for that baseline (see the parallel experiment above).
- The root-only `RDXZ64P1` format does not bind the path proof to a transaction statement, output/commitment, balance, nullifier non-reuse, ML-KEM/AES relations, or consensus acceptance. No quantified soundness, production zero-knowledge, post-quantum security, or transaction-level claim is made. This verifier is not wired to `radix_core/state.py` or `apply_block()`.

## Experimental statement-bound depth-64 path (`RDXT64P1`)

The component’s Rust functions (`prove_statement_bound_depth64_path` / `verify_statement_bound_depth64_path`) parse the strict canonical 1-in/1-out statement, use its `root_out` as the path root, and include every exact statement byte as public values in the STARK transcript. The envelope carries the statement bytes and canonical length-delimited proof; verification also requires the caller's expected statement bytes to match exactly. Tests prove a valid fixture and reject a changed fee under both caller-expected mismatch and transcript mutation, as well as malformed version/length, trailing/truncated bytes, and tampered proof payload.

This `RDXT64P1` profile retains its original arbitrary-private-leaf semantics; it is not silently upgraded by the distinct source-linked profile below. On its own, `RDXT64P1` remains only a path-membership subrelation: the private leaf is not derived from the source output record and is not linked to the public nullifier or value. The host codec exposes the exact `radix/leaf/v1` frame and padded SHAKE256 rate blocks (including the 0x9f coincident-padding boundary), but those helpers alone are not AIR constraints. Other transaction relations and a common-witness composition are absent, and neither envelope is accepted by consensus. The host codec's output-leaf consistency check is not an AIR proof of output encryption or opening.

## Experimental fixed-156-byte source-linked depth-64 path (`RDXS64P1`)

The separate `prove_source_bound_depth64_path` / `verify_source_bound_depth64_path` API and `RDXS64P1` envelope prove that a private `OutputRecordV1` source record's exact canonical `radix/leaf/v1` SHAKE256-512 digest is the leaf of a depth-64 path to the `root_out` in the exact canonical transaction statement. The source record is a private witness distinct from `statement.output`; the digest is not included as a public value. Verification checks the caller's expected statement bytes and selects this source-linked AIR profile from the distinct magic, leaving `RDXT64P1` and root-only `RDXZ64P1` unchanged.

This prototype slice is deliberately restricted to a 156-byte source ciphertext: its canonical frame is 1,359 bytes, SHAKE padding ends in the coincident 0x9f byte, and the AIR checks ten source-hash permutations followed by the existing 128 path permutations. The trace is 4,096 rows × 5,043 columns with 3,312 active round rows. A single 1,088-bit rate buffer is reused for the absorb block and final permutation output; a boundary constraint permits the rewrite only into and out of the final-round row. The source AIR consistency check and proof round trip exercise this layout. Tests cover a prove/verify round trip whose private source differs from the public output, changed source fields, mismatched source leaf/root/sibling/index, rejection of 155- and 157-byte source ciphertexts, statement/transcript mutation, and malformed or mutated envelope headers/payloads. Variable-length support is not implemented.

This proves only the source-leaf-to-path-to-statement-root relation. It does not link the source record to the public nullifier, ownership, note value, or a complete input witness; nor does it prove output encryption, value balance, or transaction validity. It remains a research-harness prototype using the test-only hiding PCS configuration, with no production zero-knowledge theorem, quantified soundness result, consensus acceptance, or production/PQ claim.

Exploratory Windows GNU Release measurements after the shared-buffer reduction (single fixture, not a benchmark): one isolated run measured 84 ms trace build, 218 ms standalone AIR check, 25.45 s valid proving for a 228,742-byte envelope, 31.9 ms verification, and 31.59 s to generate a deliberately inconsistent AIR proof that was rejected in 31.8 ms. The test took 57.79 s overall. A 300-ms process sampler observed 5,874.6 MiB peak working set and 5,883.1 MiB private bytes while generating both proofs—still very high. The pre-RDXI full serial Release suite passed 31 tests in 103.73 s; during its source test a 300-ms sampler saw 5,875.9 MiB working set and 5,931.8 MiB private bytes. Before buffer reuse, one run measured 6,131 columns, a 271,750-byte envelope, 7,114.5 MiB working set, and 7,208.8 MiB private bytes. This single-run comparison is not a benchmark or a security/resource bound. With `RAYON_NUM_THREADS=1` (before buffer reuse), valid/invalid proof generation took 98.28/100.84 s and peak memory remained about 7.1 GiB; constrained execution passed but was substantially slower. The profile needs further memory work before it is suitable for lightweight-device proving.

## Experimental composed note/source opening and depth-64 path (`RDXI64P1`)

The separate `prove_source_note_depth64_path` / `verify_source_note_depth64_path` API and `RDXI64P1` envelope compose the private note opening, private fixed-156-byte source output, and depth-64 path in one AIR/STARK. The AIR proves that `H_note(owner, value, rho, randomness)` equals the source record's 64-byte commitment, that the source record's canonical fixed-length leaf hash is the private path leaf, and that folding the path reaches `root_out` in the exact canonical statement. The note opening, source record, path, and intermediate digest remain private; the envelope carries the exact canonical statement bytes and proof. This is a composed component relation, not a full transaction proof.

The trace has 3,360 active rows (48 note-opening + 240 source-hash + 3,072 path rows), padded to 4,096 rows × 6,645 columns. Its selected hashes require 2 note, 10 source, and 128 tree-node Keccak permutations. The test exercises an AIR-level note/source commitment mismatch, stage/phase mutations, malformed or mutated envelopes, statement mismatch, and invalid note/source/index inputs, in addition to a successful prove/verify round trip.

One focused Windows GNU Release run built the RDXI trace in 114.6 ms, checked the AIR in 294.4 ms, produced a 292,822-byte envelope in 44.80 s, and verified it in 69.9 ms. A later full serial Release suite passed 33/33 tests in 206.74 s. A 250-ms sampler during that suite observed 9,444.2 MiB peak working set and 9,534.8 MiB private bytes; these single-run measurements are not benchmarks or resource bounds and show substantial memory use. No memory-constrained proving target has been validated.

`RDXI64P1` still does not prove spend-secret ownership, KEM decapsulation, nullifier derivation, output KEM/AEAD, value balance, or full transaction/state-transition rules. It uses the research harness's test-only hiding PCS profile, with no production zero-knowledge theorem, quantified soundness result, post-quantum claim, or consensus acceptance. `RDXS64P1` remains a distinct source-only profile.

## Experimental composed spend-key/owner/note/nullifier/source/path (`RDXK64P1`)

The separate `prove_source_key_note_nullifier_depth64_path` / `verify_source_key_note_nullifier_depth64_path` API and `RDXK64P1` envelope extend RDXJ in one AIR. The relation hashes private `spend_secret[64]` to `pk_s`, hashes `(pk_s, kem_shared_secret[32])` to the one-time owner used by the private note commitment, links that note to the fixed-156-byte source record and depth-64 path, and derives the public nullifier from the same spend secret, shared-secret witness, and rho. The nullifier digest is constrained to statement bytes `[175..239)` (public-values offsets `[239..303)`); all witnesses and intermediate digests remain private, while the exact canonical statement is public and transcript-bound. Profile magic is distinct from RDXI/RDXJ, and cross-profile verification is rejected.

The trace has 3,456 active rows: 24 spend-pk + 24 one-time-owner + 48 nullifier + 48 note + 240 source + 3,072 path rows, padded to 4,096 × 7,512 columns. A focused clean-source Windows GNU Release run checked the AIR in 410.3 ms, produced a 327,502-byte proof envelope in 37.68 s, and verified in 71.1 ms. The adversarial test checks nullifier-stage selectors and carries, rho carry, an interior buffer-hold mutation, block-output/rate/capacity/padding mutations, a nullifier-phase mutation, changed public nullifier statements, and host preflight rejection of a mismatched nullifier witness, in addition to a successful prove/verify round trip and cross-profile rejection. These are one-run exploratory measurements, not benchmarks; no peak-memory sample was collected for this focused run. After adding the direct interior-buffer and nullifier-phase attacks, the full serial Release suite passed 34/34 tests in 237.33 s; that run was not memory-sampled.

The first RDXK candidate failed STARK OOD verification. Disabling the buffer-hold constraints isolated the failure; replacing a nested stage-end selector with the equivalent active-transition selector `transition × nullifier_stage × (1 − final_step)` made the complete focused adversarial test pass. The AIR still constrains that the source buffer is carried unchanged except at each hash-block final row. This is a tested implementation fix, not a security proof.

`RDXK64P1` does not prove that the private shared secret is a valid ML-KEM decapsulation of the source ciphertext; nor does it prove output encryption/AEAD, enforce value balance, or verify a complete transaction. No consensus integration, production readiness, quantified soundness, ZK theorem, or post-quantum property is claimed.

## Strict host-side 1-in/1-out statement codec (not a proof)

`transaction_statement.rs` implements the experimental v1 frame for exactly one nullifier and one output. It checks fixed field widths, output-ciphertext bounds, exact vector counts, the version, output-leaf SHAKE256 consistency, the overall size limit, and byte-for-byte canonical re-encoding. The Rust output-leaf known-answer vector and serialized statement length/prefix are cross-checked against the Python reference implementation. The codec's checks are host code, not AIR constraints: `RDXS64P1` separately proves the hash of a private source record, but no current proof ties the public output record's leaf to its hidden opening/encryption relation. The statement-bound proof APIs bind statement bytes in their respective profiles. RDXL public-value construction additionally checks that the parsed statement reserializes byte-for-byte to the supplied bytes before deriving root and output fields for the AIR public vector; a lightweight regression test covers a mismatched parsed-object/byte pair. Source-leaf preflight reuses one frame for padded SHAKE blocks and digest calculation; RDXL output public-value construction reuses one frame for padded blocks. This avoids duplicate frame construction within those helpers; no timing or RSS improvement is claimed. It also does not implement Python's general 1..16 arity codec; the Python module remains the broader reference.

The codec is a foundational parsing slice only. `RDXT64P1`, `RDXS64P1`, `RDXI64P1`, `RDXJ64P1`, and `RDXK64P1` are statement-bound component envelopes, not the full transaction envelope or composed transaction prover/verifier. Parser acceptance, or any isolated path/component proof, must never be treated as transaction authorization.

## Conditions for any later soundness statement

A conditional soundness bound for this component would require a verified `ProvenSecurity` analysis for the exact complete AIR, trace and PCS configuration, along with the pinned theorem premises, accurate AirLayout and batched-function count, the actual MMCS binding assumption, Fiat–Shamir model, and proof of injective bounded-integer semantics. Such a component-only result would not establish knowledge soundness, zero knowledge, post-quantum security, or any whole-Radix security property.

The larger Candidate-A relation remains the one in `Radix-Protocol-Draft.md` §3. It still has no implemented end-to-end transaction proof system/verifier, Candidate-A transaction proof bytes/transcript, complete soundness analysis, or transaction-level zero-knowledge proof. The experimental amount-opening and note-commitment proofs close only their narrowly scoped subrelations; they do not close the transaction-proof gap.
