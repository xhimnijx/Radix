feat: the range constraint mirrored in Rust, and two implementations agree on it

The project's whole method is that two independent implementations must agree, and the range
constraint is exactly the kind of change where one side can be subtly wrong and still pass
its own tests: two new beta challenges, a shifted commitment layout, and a new term in the
verifier's equation.

  Keys.range_rows              + with_range_rows, so no existing call site changed
  paper_to_slot_ranged         the level and psi slots shift by range_count; everything
                               inside the head does not
  verifier                     draws the same betas, computes f_range, adds
                               sum beta*(f^2 + c*f)
  request format               gains a range_count field and the range rows

Measured, via experiments/cross_language_range.py: a Python proof carrying two range
messages, 22,784 bytes and 21 commitment entries, is accepted by the Rust verifier, and the
Rust verifier rejects the same proof against a different message. Both languages agree.

A STALE TEST, and the reason it matters: the Rust Gaussian test asserted the maximum sample
was 21324, which is 8 sigma. The table has been 12 sigma since the truncation change, where
the maximum is 31986, so that assertion had been failing for however long the Rust suite went
unrun. It now derives the bound from the table's own sigma and asserts the value explicitly,
so the next change to the truncation is deliberate rather than silent. This is the second
time a number in this project was right when written and wrong later; the check is now tied
to the data rather than to a memory.

70 Rust tests, 603 Python tests, 1 known xfail.
